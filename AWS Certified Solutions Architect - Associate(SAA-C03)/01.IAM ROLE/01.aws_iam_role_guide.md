# AWS IAM 역할(Role) 생성 및 신뢰할 수 있는 엔티티 가이드

## 1. IAM 역할 생성 화면 개요
현재 확인한 화면은 AWS Management Console의 **IAM > Roles > Create role** 경로에서 진행하는 **역할(Role) 생성 1단계**입니다.

* **진행 상태:** *"26. IAM Role 실습"* 강의 기준 1단계(`Select trusted entity`)에서 **AWS service**가 선택되어 있습니다.
* **다음 작업:** 하단의 **Use case(사용 사례)** 드롭다운 메뉴(`Service or use case`)에서 이 역할을 실제로 사용할 구체적인 AWS 서비스(예: EC2, Lambda 등)를 선택한 뒤 다음 단계로 넘어갑니다.

### IAM 역할 생성 3단계 프로세스
1. **Select trusted entity (신뢰할 수 있는 엔티티 선택):** 이 역할을 맡아서 사용할 주체와 구체적인 사용 사례를 지정합니다.
2. **Add permissions (권한 추가):** 이 역할이 AWS 리소스에 대해 어떤 작업을 수행할 수 있는지 정의하는 IAM 정책(Policy)을 연결합니다.
3. **Name, review, and create (이름 지정, 검토 및 생성):** 역할의 이름을 입력하고 신뢰 관계 및 권한 설정을 최종 검토한 뒤 생성을 완료합니다.

---

## 2. Trusted entity type(신뢰할 수 있는 엔티티 유형) 구분 기준
5가지 항목은 **'누가(또는 무엇이) 이 역할의 권한을 임시로 빌려 쓸 것인가'**라는 **주체의 위치와 인증 방식**을 기준으로 나뉩니다.

* **위치 기준:** 현재 AWS 계정 내부의 리소스가 사용하는지, 아니면 계정 밖의 다른 AWS 계정이나 외부 시스템이 사용하는지에 따라 구분됩니다.
* **인증 방식 기준:** 외부에서 접근할 때 AWS 자체 계정을 쓰는지, 소셜/웹 로그인을 쓰는지, 기업용 사내 통합 인증(SSO)을 쓰는지, 혹은 특수한 조건을 직접 코드로 작성하는지에 따라 나뉩니다.

---

## 3. 각 항목별 상세 설명

### ① AWS service (AWS 서비스)
* **대상:** 현재 계정 내의 EC2, Lambda, ECS 같은 AWS 리소스입니다.
* **용도:** 서버나 코드가 S3 버킷에 파일을 올리는 등 다른 AWS 서비스에 접근해야 할 때 사용합니다. 보안에 취약한 액세스 키를 서버 내부에 직접 저장하지 않고 안전하게 권한을 부여하기 위해 가장 많이 쓰입니다.

### ② AWS account (AWS 계정)
* **대상:** 내가 관리하는 또 다른 AWS 계정이나 외부 파트너사(제3자)의 AWS 계정입니다.
* **용도:** 여러 개의 AWS 계정을 운영할 때, A 계정의 사용자가 B 계정의 리소스를 관리할 수 있도록 교차 계정 접근(Cross-account access) 권한을 줄 때 선택합니다.

### ③ Web identity (웹 자격 증명)
* **대상:** Amazon Cognito나 Google, Facebook, Apple 같은 외부 웹 인증 공급자(IdP)를 통해 로그인한 일반 사용자입니다.
* **용도:** 모바일 앱이나 웹 서비스 사용자에게 개별 AWS 계정을 만들어주지 않고도, 소셜 로그인 인증만으로 S3 등 특정 AWS 리소스에 직접 접근할 수 있는 임시 권한을 줄 때 사용합니다.

### ④ SAML 2.0 federation (SAML 2.0 연동)
* **대상:** Active Directory(AD)나 Okta 같은 기업용 사내 통합 인증 시스템을 사용하는 회사 임직원입니다.
* **용도:** 직원들이 사내 계정으로 한 번만 로그인(SSO)하면 별도의 AWS 로그인 없이도 회사 AWS 콘솔이나 리소스에 접속할 수 있도록 연동할 때 사용합니다.

### ⑤ Custom trust policy (사용자 지정 신뢰 정책)
* **대상:** 위의 4가지 기본 템플릿으로 표현하기 어려운 복합적이거나 특수한 주체입니다.
* **용도:** 여러 조건을 동시에 걸거나 특정 태그가 붙은 리소스만 역할을 쓰게 하는 등 JSON 코드로 직접 세밀한 신뢰 정책을 작성해야 할 때 선택합니다.

## 4. '각 항목에 Role을 부여한다'의 의미

**Role(역할)을 부여한다**는 것은 특정 대상에게 **"영구적인 계정을 만들어주는 대신, 필요할 때마다 임시 신분증(보안 자격 증명)을 빌려 쓰고 내 계정의 리소스에 접근해도 좋다"**고 허락해 주는 것을 의미합니다.

### 쉬운 비유: '일회용 출입증'
* **IAM User (사용자):** 회사 정직원 사원증입니다. 영구적인 아이디와 비밀번호가 있습니다.
* **IAM Role (역할):** 방문객이나 특정 업무를 맡은 대상에게 잠시 빌려주는 **'임시 출입증'**입니다.
* **Trusted entity (신뢰할 수 있는 엔티티):** 이 임시 출입증을 **"누구에게 빌려줄 것인가"**를 정하는 규칙입니다.

### 항목별 실제 동작 의미
* **AWS service에 부여:** EC2 같은 기계에 아이디/비밀번호를 직접 넣지 않고, AWS가 알아서 임시 출입증을 발급·갱신해 주어 안전하게 S3 등에 접근하게 합니다.
* **AWS account에 부여:** 외부 협력사 엔지니어 등 다른 계정 사용자에게 우리 회사 계정을 새로 만들어주지 않고, 기존 본인 계정으로 잠시 권한을 넘겨받아 작업하게 합니다.
* **Web identity에 부여:** 앱 사용자마다 AWS 계정을 생성해 줄 수 없으므로, 소셜 로그인 인증이 확인되면 잠시 사진을 업로드할 수 있는 임시 권한을 빌려줍니다.
* **SAML 2.0 federation에 부여:** 사내 포털에 한 번만 로그인한 임직원에게 별도의 AWS 계정 비밀번호 없이 직급에 맞는 AWS 콘솔 출입증을 자동으로 발급합니다.
* **Custom trust policy에 부여:** "특정 IP에서 접속했고 특정 시간대에 요청한 경우에만 출입증을 빌려준다"처럼 까다로운 발급 조건을 JSON으로 직접 정의합니다.
