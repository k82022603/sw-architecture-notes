# AWS IAM Role(역할) 심층 기술 가이드: 아키텍처, 신뢰 정책, 인증 흐름 및 실전 활용

본 문서는 AWS IAM(Identity and Access Management)의 핵심 개념인 **IAM Role(역할)**의 내부 동작 원리, **신뢰할 수 있는 엔티티(Trusted Entity) 5가지 유형의 심층 비교**, **STS(Security Token Service) 기반 임시 자격 증명 발급 메커니즘**, 그리고 **실무 아키텍처 시나리오 및 정책(Policy) 구조**를 상세히 다룹니다.

---

## 1. IAM Role의 핵심 아키텍처 및 개념

### 1.1 IAM User vs IAM Role: 왜 Role을 사용하는가?
AWS에서 권한을 부여하는 방식은 크게 영구 자격 증명(`IAM User`)과 임시 자격 증명(`IAM Role`)으로 나뉩니다.

| 구분 | IAM User (사용자) | IAM Role (역할) |
| :--- | :--- | :--- |
| **자격 증명 유형** | 영구적 (비밀번호, Access Key / Secret Key) | 일시적 (STS를 통한 임시 토큰: AccessKeyId, SecretAccessKey, SessionToken) |
| **대상 주체** | 특정 개인 또는 고정된 단일 애플리케이션 | AWS 서비스, 다른 AWS 계정, 외부 인증(IdP) 사용자 등 불특정 다수/리소스 |
| **보안 위험성** | 키 유출 시 만료 전까지 무제한 악용 가능 (수동 로테이션 필요) | 설정된 세션 시간(15분~12시간) 후 자동 만료되어 유출 피해 최소화 |
| **권한 위임 방식** | 사용자에게 직접 권한 정책(Permission Policy) 연결 | **신뢰 정책(Trust Policy)**으로 수임 대상을 제한하고, **권한 정책**으로 작업 범위 지정 |

### 1.2 Role을 구성하는 두 가지 핵심 정책 (Two-Policy Model)
IAM Role이 작동하려면 반드시 두 종류의 JSON 문서(정책)가 결합되어야 합니다.

1. **신뢰 정책 (Trust Policy) - "누가 이 역할을 쓸 수 있는가?"**
   * 콘솔의 **Step 1 (Select trusted entity)**에서 설정하는 내용입니다.
   * `sts:AssumeRole` (또는 `AssumeRoleWithWebIdentity`, `AssumeRoleWithSAML`) 액션을 수행할 수 있는 주체(`Principal`)를 정의합니다.
2. **권한 정책 (Permissions Policy) - "이 역할을 쓰면 무엇을 할 수 있는가?"**
   * 콘솔의 **Step 2 (Add permissions)**에서 연결하는 내용입니다.
   * 역할을 수임(Assume)한 주체가 S3, EC2, DynamoDB 등의 AWS 리소스에 대해 실행할 수 있는 구체적인 API 작업(`Action`)과 대상(`Resource`)을 정의합니다.

## 2. Trusted Entity Type(신뢰할 수 있는 엔티티 유형) 5가지 심층 분석

콘솔 화면의 5가지 선택지는 **요청 주체의 위치(내부 vs 외부)**와 **신원 검증 프로토콜(AWS 내부 인증, 교차 계정, OIDC, SAML 2.0, 커스텀 조건)**을 기준으로 설계되었습니다.

### 2.1 AWS service (AWS 서비스)
* **기술적 배경:** 현재 AWS 계정 내에 배포된 컴퓨팅 또는 관리형 서비스(EC2, Lambda, ECS, RDS, Glue 등)가 다른 AWS 서비스 API를 호출해야 할 때 사용합니다.
* **동작 원리 (EC2 예시):**
  1. IAM Role을 EC2 인스턴스 프로파일(Instance Profile)에 연결합니다.
  2. EC2 내부의 애플리케이션(AWS SDK/CLI)이 S3에 접근하려 할 때, 코드에 키를 적지 않아도 SDK가 자동으로 인스턴스 메타데이터 서비스(**IMDSv2**, `http://169.254.169.254/latest/meta-data/iam/security-credentials/`)를 조회합니다.
  3. AWS가 백그라운드에서 발급하고 주기적으로 자동 갱신해 주는 임시 자격 증명을 받아 S3 요청에 서명합니다.
* **신뢰 정책(Trust Policy) 예시:**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

### 2.2 AWS account (AWS 계정)
* **기술적 배경:** 멀티 계정(Multi-Account) 아키텍처(예: 개발/스테이징/운영 계정 분리, 보안 감사 계정 분리) 또는 외부 제3자(SaaS 벤더, 파트너사)에게 내 계정의 리소스 접근 권한을 위임할 때 사용합니다.
* **핵심 보안 옵션:**
  * **External ID (외부 ID):** 제3자(파트너사)에게 권한을 줄 때 필수적으로 권장되는 보안 장치입니다. 혼동된 대리자 문제(Confused Deputy Problem)를 방지하기 위해 파트너사가 제공한 고유 ID를 조건(`Condition`)에 걸어 검증합니다.
  * **MFA 필수화:** 역할을 전환(`Switch Role`)할 때 반드시 다중 인증(MFA)을 거치도록 강제할 수 있습니다.
* **신뢰 정책(Trust Policy) 예시 (제3자 계정 + External ID 검증):**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:root"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "unique-partner-secret-id-9876"
        }
      }
    }
  ]
}
```

### 2.3 Web identity (웹 자격 증명)
* **기술적 배경:** **OIDC(OpenID Connect)** 표준을 기반으로 외부 웹/모바일 인증 공급자(Amazon Cognito, Google, Apple, Facebook, Auth0, 또는 GitHub Actions 등)에서 발급받은 JWT(ID Token)를 AWS 임시 자격 증명과 교환하는 방식입니다.
* **동작 원리:**
  1. 모바일 앱 사용자가 Google 계정으로 로그인하여 Google로부터 OIDC ID 토큰을 받습니다.
  2. 앱이 AWS STS의 `AssumeRoleWithWebIdentity` API를 호출하면서 이 토큰을 전달합니다.
  3. AWS IAM이 Google의 공개키로 토큰의 서명과 유효성을 검증한 뒤, 해당 사용자에게 지정된 IAM Role의 임시 자격 증명을 반환합니다.
  4. 앱은 이 임시 키를 사용해 중간 백엔드 서버를 거치지 않고도 S3 버킷의 특정 폴더(예: `s3://my-app-bucket/users/${cognito-identity.amazonaws.com:sub}/*`)에 직접 파일을 업로드할 수 있습니다.
* **신뢰 정책(Trust Policy) 예시:**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "cognito-identity.amazonaws.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "cognito-identity.amazonaws.com:aud": "ap-northeast-2:11112222-3333-4444-5555-666677778888"
        }
      }
    }
  ]
}
```

### 2.4 SAML 2.0 federation (SAML 2.0 연동)
* **기술적 배경:** 대기업 환경에서 사내 디렉터리 서비스(Microsoft Entra ID / Active Directory, Okta, OneLogin, Ping Identity 등)를 사용하는 임직원에게 **SSO(Single Sign-On)**를 통해 AWS Management Console 및 CLI 접근 권한을 부여할 때 사용합니다.
* **동작 원리:**
  1. 임직원이 사내 포털(IdP)에 사번과 비밀번호로 로그인합니다.
  2. IdP가 사용자의 부서/직급 속성이 담긴 암호화된 **SAML Assertion(XML 문서)**을 생성하여 브라우저를 통해 AWS 로그인 엔드포인트(`https://signin.aws.amazon.com/saml`)로 전송합니다.
  3. AWS STS의 `AssumeRoleWithSAML`이 이를 검증하고, 사내 그룹에 매핑된 IAM Role(예: `DevOps-Admin-Role`, `ReadOnly-Audit-Role`)의 임시 세션을 열어 콘솔 화면으로 즉시 리다이렉트합니다.
  4. 퇴사자가 사내 AD에서 비활성화되면 즉시 AWS 접근도 차단되므로 중앙 집중식 계정 관리가 가능해집니다.

### 2.5 Custom trust policy (사용자 지정 신뢰 정책)
* **기술적 배경:** 콘솔 UI가 제공하는 단일 주체 템플릿의 한계를 넘어, 복합적인 주체 결합이나 세밀한 ABAC(Attribute-Based Access Control, 속성 기반 접근 제어) 조건을 JSON으로 직접 작성할 때 사용합니다.
* **주요 활용 사례:**
  * 하나의 Role을 EC2 서비스(`ec2.amazonaws.com`)와 특정 IAM 사용자(`arn:aws:iam::...`)가 동시에 사용할 수 있도록 다중 `Principal` 지정.
  * `aws:PrincipalTag` 조건을 걸어 리소스 태그(`Project=Alpha`)와 Role 태그가 일치할 때만 역할 수임을 허용.
  * `aws:SourceIp` 또는 `aws:SourceVpce` 조건을 추가해 특정 사내 망 IP나 특정 VPC 엔드포인트를 통해서만 역할을 빌려 갈 수 있도록 네트워크 수준 통제.

## 3. "각 항목에 Role을 부여한다"는 것의 실제 메커니즘 (STS 흐름)

AWS에서 "Role을 부여한다"는 표현은 물리적으로 권한을 복사해 주는 것이 아니라, **AWS STS(Security Token Service)를 통한 동적 토큰 교환(Token Exchange)**을 허용한다는 뜻입니다.

### 전체 인증 및 권한 행사 4단계 파이프라인
1. **신뢰 관계 사전 구성 (관리자 작업):**
   * 관리자가 Role을 생성하면서 Trust Policy에 "주체 A가 `AssumeRole`을 요청하면 허락한다"고 명시하고, Permissions Policy에 "S3 읽기 권한"을 붙입니다.
2. **역할 수임 요청 (AssumeRole Request):**
   * 주체 A(EC2, 타 계정 사용자, 웹/SAML 인증 사용자 등)가 자신의 기존 신원 증명을 제시하며 AWS STS에 `AssumeRole` API를 호출합니다.
3. **임시 자격 증명 발급 (Temporary Credentials Issuance):**
   * STS는 Role의 Trust Policy를 검사하여 주체 A가 허가된 대상인지 확인합니다.
   * 검증이 통과되면 유효기간(예: 1시간)이 설정된 3가지 값(**AccessKeyId**, **SecretAccessKey**, **SessionToken**)을 반환합니다.
4. **리소스 접근 및 권한 평가 (API Execution):**
   * 주체 A는 발급받은 임시 토큰 3종 세트를 사용하여 S3 API(`GetObject`)를 호출합니다.
   * AWS IAM 엔진은 해당 토큰에 연결된 Role의 Permissions Policy를 평가하여 요청을 최종 승인(`Allow`)하거나 거부(`Deny`)합니다.

## 4. 실습 및 실무 적용을 위한 모범 사례 (Best Practices)

* **최소 권한 원칙 (Least Privilege):** 실습 단계에서는 편의상 `AdministratorAccess`나 `AmazonS3FullAccess`를 붙이기도 하지만, 실무에서는 반드시 필요한 특정 버킷 ARN과 특정 액션(`s3:GetObject`, `s3:PutObject`)만 허용하는 고객 관리형 정책(Customer Managed Policy)을 작성하여 연결해야 합니다.
* **절대 하드코딩 금지:** EC2, Lambda, GitHub Actions, 로컬 개발 환경 등 어디에도 영구적인 `AWS_ACCESS_KEY_ID`를 코드나 설정 파일에 저장하지 말고, 반드시 환경에 맞는 Trusted Entity 유형(AWS service 또는 Web identity OIDC)의 Role을 사용해야 합니다.
* **권한 경계 (Permissions Boundary) 활용:** 개발자에게 직접 IAM Role을 생성할 권한을 위임해야 할 경우, 생성되는 Role이 가질 수 있는 최대 권한의 상한선(Permissions Boundary)을 강제하여 권한 상승(Privilege Escalation) 공격을 원천 차단합니다.
* **CloudTrail 감사 로그 모니터링:** 모든 `AssumeRole` 이벤트와 임시 자격 증명으로 수행된 API 호출은 AWS CloudTrail에 기록되므로, 비정상적인 시간대나 알 수 없는 IP에서의 역할 수임 시도를 경보(CloudWatch Alarms)로 설정해 두는 것이 안전합니다.
