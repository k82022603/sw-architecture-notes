## Question 1: 장기 약정 할인과 유연성 (Savings Plans vs Reserved Instances)

**Scenario:**
A company runs a steady-state web application on Amazon EC2 instances 24 hours a day. The company expects to keep running the workload for the next 3 years. However, the engineering team plans to migrate from Intel-based M5 instances to AWS Graviton-based instances next year and may move part of the workload to another AWS Region. The company wants the LOWEST cost while keeping the flexibility to change instance families and Regions. Which purchasing option should a solutions architect recommend?

* **A.** Purchase 3-year Standard Reserved Instances for the M5 instance type in the current Region.
* **B.** Run all instances as On-Demand Instances and add an On-Demand Capacity Reservation.
* **C.** Purchase a 3-year Compute Savings Plan with a commitment based on the expected hourly spend.
* **D.** Run all instances as Spot Instances with a persistent Spot request.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **C**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** "오래 쓸 것이 확실하지만 인스턴스 구성은 바뀔 수 있다"는 조건에서 **구성이 아니라 사용량을 약정**하는 Savings Plans를 고르는 문제입니다.
* **정답 분석 (C):** AWS 문서에 따르면 Savings Plans는 특정 인스턴스 구성이 아니라 시간당 USD 기준의 일정한 사용량을 1년 또는 3년 동안 약정하는 방식입니다. 여러 인스턴스 패밀리와 리전에 걸쳐 적용되는 것은 **Compute Savings Plans**입니다. 반면 EC2 Instance Savings Plans는 특정 인스턴스 패밀리와 리전에 묶인다는 점을 함께 기억해야 합니다. AWS 요금 안내는 Reserved Instances보다 Savings Plans를 권장한다고 밝히고 있고, 할인 폭은 온디맨드 대비 최대 72%라고 적고 있습니다. 최대 72%는 AWS가 밝힌 상한이며 실제 할인율은 조건에 따라 다릅니다.
* **오답 분석:**
  * **A:** Reserved Instances는 인스턴스 유형과 리전 같은 특정 구성을 약정합니다. M5에서 Graviton으로 옮기거나 리전을 바꾸면 약정이 맞지 않게 됩니다.
  * **B:** On-Demand는 약정이 없는 대신 단가가 가장 높습니다. Capacity Reservation은 용량 확보 수단이지 할인 수단이 아닙니다.
  * **D:** Spot은 중단될 수 있으므로 24시간 안정적으로 돌아야 하는 웹 애플리케이션에 맞지 않습니다.
</details>

## Question 2: 특정 AZ의 용량 확보 (Capacity Reservation)

**Scenario:**
An e-commerce company expects a large traffic increase during a 2-week sales event. The company needs to guarantee that 30 compute-optimized instances can be launched in a specific Availability Zone at any time during the event. The company already has a Compute Savings Plan and does not want a long-term commitment for the extra capacity. Which solution meets these requirements?

* **A.** Purchase additional Compute Savings Plans to cover the event.
* **B.** Create On-Demand Capacity Reservations in the specific Availability Zone for the duration of the event.
* **C.** Purchase 1-year zonal Reserved Instances for the specific Availability Zone.
* **D.** Use Spot Instances in the specific Availability Zone with a high maximum price.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **B**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **할인(비용)과 용량 보장은 서로 다른 문제**라는 점을 구분하는 문제입니다.
* **정답 분석 (B):** AWS 문서는 특정 AZ의 용량 예약이 필요하면 Reserved Instances나 **Capacity Reservations**를 쓰라고 안내합니다. Capacity Reservation은 약정 기간이 없어 필요한 기간만 만들고 끝나면 취소할 수 있습니다. 이미 가진 Savings Plans 할인은 예약한 용량의 사용 요금에도 적용할 수 있습니다. 예약한 용량은 쓰지 않아도 온디맨드 요금이 청구된다는 점이 일반적인 설명이며, 이벤트 기간에 맞춰 만들고 취소하는 운용이 비용 면에서 중요합니다.
* **오답 분석:**
  * **A:** Savings Plans는 비용을 낮춰 줄 뿐 용량을 예약해 주지 않습니다. AWS 문서도 용량 예약이 필요하면 별도 수단을 쓰라고 구분합니다.
  * **C:** 1년짜리 zonal Reserved Instances는 용량 예약 효과가 있지만, "장기 약정을 원하지 않는다"는 조건에 어긋납니다.
  * **D:** Spot은 AWS가 용량을 회수할 수 있어 "언제든 시작할 수 있어야 한다"는 보장을 줄 수 없습니다.
</details>

## Question 3: 초고성능 데이터베이스 볼륨 (io2 Block Express)

**Scenario:**
A company runs a mission-critical Oracle OLTP database on a single Amazon EC2 instance. The database requires a single Amazon EBS volume that can deliver 150,000 IOPS with consistent sub-millisecond latency. The volume must be designed for the highest durability among EBS volume types. Which EBS volume type should a solutions architect choose?

* **A.** General Purpose SSD (gp3) volume with the maximum provisioned IOPS and throughput.
* **B.** An EC2 instance store volume on a storage optimized instance.
* **C.** Throughput Optimized HDD (st1) volume.
* **D.** Provisioned IOPS SSD (io2 Block Express) volume.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **D**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 볼륨 하나가 낼 수 있는 **IOPS 상한**과 **내구성 등급**으로 볼륨 유형을 가려내는 문제입니다.
* **정답 분석 (D):** AWS 볼륨 유형 페이지 기준으로 io2 Block Express는 볼륨당 최대 256,000 IOPS, 최대 4,000 MB/s, 최대 64 TB를 제공하고 내구성은 99.999%입니다. 16 KiB 입출력에서 평균 지연 시간이 500마이크로초 미만이 되도록 설계되었다고 AWS가 밝히고 있습니다. 이 수치들은 모두 AWS가 제시한 사양이며, 150,000 IOPS와 최고 내구성 요건을 모두 충족하는 것은 io2 Block Express뿐입니다.
* **오답 분석:**
  * **A:** gp3는 볼륨당 최대 프로비저닝 IOPS가 80,000이고 최대 처리량이 2,000 MiB/s입니다. 150,000 IOPS에는 모자랍니다. 내구성도 99.8%~99.9%입니다.
  * **B:** 인스턴스 스토어는 인스턴스가 중지되거나 종료되면 데이터가 사라지는 임시 저장소라서 미션 크리티컬 데이터베이스의 내구성 요건을 충족하지 못합니다.
  * **C:** st1은 볼륨당 최대 IOPS가 500 수준으로, 순차 처리량용 HDD라서 OLTP에 맞지 않습니다.

> 암기: **80,000 IOPS를 넘으면 io2 Block Express**, 내구성 99.999%도 io2 Block Express.
</details>

## Question 4: 대용량 순차 처리 (st1)

**Scenario:**
A company runs a log-processing cluster on Amazon EC2 that reads and writes large sequential files. The cluster needs a 12 TB data volume per instance. The workload is throughput-intensive, the data is accessed frequently, and the volume is NOT used as a boot volume. The company wants the LOWEST cost per GB that still meets the access pattern. Which EBS volume type should the company use?

* **A.** General Purpose SSD (gp3)
* **B.** Throughput Optimized HDD (st1)
* **C.** Provisioned IOPS SSD (io2 Block Express)
* **D.** Cold HDD (sc1)

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **B**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **자주 접근하는 대용량 순차 처리 워크로드**에 맞는 HDD 유형을 고르는 문제입니다. 키워드는 `large sequential`, `throughput-intensive`, `frequently accessed`, `lowest cost`입니다.
* **정답 분석 (B):** AWS 페이지 기준으로 st1은 125 GB~16 TB 크기에, 최대 처리량 500 MB/s를 제공하며 빅데이터, 데이터 웨어하우스, 로그 처리처럼 자주 접근하는 처리량 중심 워크로드를 대상으로 합니다. HDD라서 일반적으로 GB당 단가가 SSD보다 낮습니다. 12 TB는 st1의 크기 범위(최대 16 TB) 안입니다.
* **오답 분석:**
  * **A:** gp3도 사용할 수는 있지만 SSD여서 GB당 비용이 더 높습니다. "가장 낮은 비용"이라는 조건에서 밀립니다.
  * **C:** io2 Block Express는 지연 시간에 민감한 트랜잭션용이며 비용이 가장 큰 축에 속합니다.
  * **D:** sc1은 **접근 빈도가 낮은 콜드 데이터**용입니다. 최대 처리량이 250 MB/s로 st1보다 낮고, 문제는 "자주 접근한다"고 못박았습니다.

> 암기: HDD(st1, sc1)는 **부트 볼륨으로 쓸 수 없습니다**. 문제에서 "부트 볼륨"이 나오면 SSD(gp3 등)를 고르세요.
</details>

## Question 5: gp2에서 gp3로 중단 없이 전환 (Elastic Volumes)

**Scenario:**
A company has 200 Amazon EBS General Purpose SSD (gp2) volumes attached to production EC2 instances. Each volume needs no more than 3,000 IOPS. The company wants to reduce storage cost with NO downtime and the LEAST operational effort. Which solution meets these requirements?

* **A.** Use Amazon EBS Elastic Volumes to modify the volume type of each existing volume to gp3.
* **B.** Stop each instance, create a snapshot of each volume, and restore the snapshot as a gp3 volume.
* **C.** Replace each volume with an io2 Block Express volume and set the minimum IOPS.
* **D.** Replace each volume with a Throughput Optimized HDD (st1) volume.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **EBS Elastic Volumes**로 서비스 중단 없이 볼륨 유형, 크기, 성능을 바꿀 수 있다는 점과 **gp3의 비용 이점**을 묻는 문제입니다.
* **정답 분석 (A):** AWS 문서에 따르면 gp3는 GiB당 가격이 gp2보다 20% 낮고, 기본으로 3,000 IOPS와 125 MiB/s가 스토리지 가격에 포함됩니다. 기존 gp2 볼륨은 Elastic Volumes 기능으로 **인스턴스를 중단하지 않고** gp3로 바꿀 수 있다고 문서가 안내합니다. 3,000 IOPS 이하가 필요하다면 gp3의 기본 성능으로 충분하므로, 유형만 바꾸면 비용이 줄어듭니다. (참고: gp2는 크기에 비례해 GiB당 3 IOPS를 주기 때문에, 1,000 GiB보다 작은 볼륨은 3,000 IOPS를 기준 성능으로 얻지 못하고 버스트 크레딧에 의존합니다. gp3는 버스트 없이 3,000 IOPS를 유지합니다.)
* **오답 분석:**
  * **B:** 인스턴스를 멈추고 스냅샷을 복원하는 방식은 다운타임과 운영 작업이 큽니다.
  * **C:** io2 Block Express는 오히려 비용이 늘어납니다. 비용 절감 목표에 반대입니다.
  * **D:** st1은 HDD라서 부트 볼륨이나 낮은 지연이 필요한 트랜잭션에 맞지 않고, 성능 특성이 달라 서비스에 영향이 생길 수 있습니다.
</details>

## Question 6: EBS 볼륨을 다른 AZ로 옮기기 (Snapshot)

**Scenario:**
An application runs on an EC2 instance in us-east-1a. The instance uses an additional Amazon EBS data volume. The company must move the application to us-east-1b and keep all data from the EBS volume. What should a solutions architect do?

* **A.** Detach the EBS volume and attach it directly to a new EC2 instance in us-east-1b.
* **B.** Enable EBS Multi-Attach and attach the same volume to an instance in us-east-1b.
* **C.** Create a snapshot of the EBS volume, create a new volume from the snapshot in us-east-1b, and attach the new volume to an instance in us-east-1b.
* **D.** Configure Amazon S3 Cross-Region Replication on the EBS volume.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **C**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **EBS 볼륨은 하나의 AZ에 묶여 있고**, 같은 AZ의 인스턴스에만 연결할 수 있다는 성질을 묻는 문제입니다.
* **정답 분석 (C):** AWS 문서에 따르면 EBS 볼륨은 생성된 AZ 안에서 복제되고, 같은 AZ의 EC2 인스턴스에만 연결할 수 있습니다. 다른 AZ로 옮기려면 **스냅샷을 만들고, 스냅샷으로 대상 AZ에 새 볼륨을 만드는** 방식을 씁니다. 스냅샷은 S3에 저장되어 여러 AZ에 중복 보관되며, 새 볼륨은 스냅샷 시점의 정확한 복사본입니다.
* **오답 분석:**
  * **A:** 다른 AZ의 인스턴스에는 볼륨을 직접 붙일 수 없습니다.
  * **B:** Multi-Attach도 **같은 AZ** 안의 인스턴스 사이에서만 동작합니다. AZ를 넘는 기능이 아닙니다.
  * **D:** S3 Cross-Region Replication은 S3 객체 복제 기능이며 EBS 볼륨에 적용하는 기능이 아닙니다.

> 암기: EBS는 **AZ 종속**, AZ/리전을 넘기려면 **스냅샷**.
</details>

## Question 7: 같은 볼륨을 여러 인스턴스에 연결 (Multi-Attach)

**Scenario:**
A company runs a clustered application on two Nitro-based EC2 instances in the same Availability Zone. The application uses a cluster-aware file system and requires both instances to read from and write to the SAME block storage volume at the same time. The company needs the highest possible performance. Which solution meets these requirements?

* **A.** Create a gp3 volume and enable Multi-Attach.
* **B.** Create two st1 volumes and attach one to each instance.
* **C.** Create one EBS volume in each Availability Zone and attach each volume to one instance.
* **D.** Create an io2 Block Express volume and enable Multi-Attach.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **D**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** EBS는 보통 **인스턴스 한 대에만 붙는** 블록 스토리지이며, 예외인 **Multi-Attach**의 지원 유형과 조건을 묻는 문제입니다.
* **정답 분석 (D):** AWS 문서에 따르면 io2 Block Express 볼륨은 I/O fencing을 포함한 Multi-Attach를 지원하며, **같은 AZ의 Nitro 기반 EC2 인스턴스 최대 16대**에 동시에 연결할 수 있습니다. Multi-Attach로 붙인 볼륨은 여러 인스턴스가 동시에 쓰기를 하므로 **클러스터 인식 파일 시스템**이 필요합니다. 문제에서 이 조건이 제시되었습니다.
* **오답 분석:**
  * **A:** Multi-Attach는 프로비저닝 IOPS SSD(io1, io2) 계열에서 지원하는 기능이며, gp3는 지원 대상이 아닙니다. (AWS 문서에서 Multi-Attach 지원 유형 목록을 직접 대조해 확인하지는 못했으며 시험에서 널리 알려진 규칙입니다.)
  * **B:** 마찬가지로 볼륨이 분리되어 있고, st1은 이 용도에 맞지 않습니다.
  * **C:** 볼륨이 각각 따로 존재해 같은 데이터를 공유하지 못합니다.

> 암기: Multi-Attach = **io2(Provisioned IOPS) + Nitro + 같은 AZ + 최대 16대 + 클러스터 인식 파일 시스템**. 여러 인스턴스가 **일반 공유 파일**을 쓰는 문제라면 EFS가 답입니다.
</details>

## Question 8: 임시 고성능 저장소 (Instance Store)

**Scenario:**
A company runs a data-processing job on EC2 that needs very high-speed temporary scratch space. The intermediate data can be regenerated from the source data at any time, and the final results are written to Amazon S3. The company wants the highest I/O performance at the lowest cost for the scratch space. Which solution should a solutions architect recommend?

* **A.** Mount an Amazon EFS file system for scratch data.
* **B.** Attach an io2 Block Express volume for scratch data.
* **C.** Use a storage optimized EC2 instance and use its local instance store NVMe volumes for scratch data.
* **D.** Write all intermediate data directly to Amazon S3 Standard.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **C**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 데이터를 잃어도 되는 **임시 데이터**에는 인스턴스 스토어를, 내구성이 필요한 데이터에는 EBS 등을 고르는 문제입니다.
* **정답 분석 (C):** 인스턴스 스토어는 호스트에 물리적으로 붙은 로컬 디스크(NVMe)라서 네트워크를 거치지 않아 입출력 성능이 높고, 인스턴스 비용에 포함되어 별도 스토리지 요금이 없습니다. 대신 인스턴스가 중지·종료되거나 하드웨어에 문제가 생기면 데이터가 사라집니다. 문제에서 중간 결과는 언제든 다시 만들 수 있고 최종 결과는 S3에 쓴다고 했으므로 조건에 맞습니다. 최신 세대에도 로컬 NVMe를 가진 계열이 계속 나오고 있으며, 예를 들어 R8idn은 최대 22,800 GB의 로컬 NVMe 스토리지를 제공한다고 AWS가 2026년 공지에서 밝혔습니다.
* **오답 분석:**

## Question 9: 고정 IP와 초저지연 UDP (Network Load Balancer)

### 상세 해설 (Korean)

## Question 11: AZ 간 트래픽 쏠림 (Cross-Zone Load Balancing)

**Scenario:**
A company uses a Network Load Balancer across two Availability Zones. Two EC2 targets are registered in AZ-A and eight EC2 targets are registered in AZ-B. Monitoring shows that the two instances in AZ-A are heavily loaded while the eight instances in AZ-B are mostly idle. The company wants traffic to be spread evenly across all ten targets. What should a solutions architect do?

* **A.** Enable cross-zone load balancing on the Network Load Balancer.
* **B.** Disable cross-zone load balancing on the Network Load Balancer.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

## Question 15 (Multiple Choice, Select TWO): ALB와 Auto Scaling 연동

**Scenario:**
A company wants EC2 instances launched by an Auto Scaling group to automatically receive traffic from an Application Load Balancer. The company also wants the Auto Scaling group to replace any instance that the load balancer reports as unhealthy. Which TWO steps should a solutions architect take? (Select TWO.)

* **A.** Attach the load balancer's target group (target type `instance`) to the Auto Scaling group.
* **B.** Turn on Elastic Load Balancing health checks for the Auto Scaling group.
* **C.** Create an AWS Lambda function that registers each new instance in the target group.
* **D.** Create the target group with target type `ip` and register each instance's private IP address manually.
* **E.** Assign an Elastic IP address to every instance and add them to the Application Load Balancer.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A, B**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** ASG와 로드 밸런서를 연결하는 방식, 즉 **대상 그룹 연결**과 **ELB 헬스 체크 활성화**를 묻는 문제입니다.
* **정답 분석 (A):** ALB, NLB, GWLB를 쓸 때는 로드 밸런서 자체가 아니라 **대상 그룹(target group)**을 Auto Scaling 그룹에 연결합니다. 연결하면 ASG가 시작한 인스턴스는 대상 그룹에 **자동으로 등록**되고 종료된 인스턴스는 자동으로 등록 해제됩니다. AWS 문서에 따르면 ASG와 함께 쓰는 대상 그룹의 대상 유형은 `instance`여야 하고, 로드 밸런서와 ASG는 같은 계정, VPC, 리전에 있어야 합니다.
* **정답 분석 (B):** ASG는 기본적으로 EC2 상태 점검만 보므로, 로드 밸런서가 비정상으로 판단한 인스턴스를 교체하려면 **ELB 헬스 체크를 켜야** 합니다. 켜면 EC2 헬스 체크와 ELB 헬스 체크 중 하나라도 실패하는 인스턴스는 비정상으로 간주됩니다.
* **오답 분석:**
  * **C:** 등록과 해제는 ASG가 자동으로 처리하므로 Lambda를 따로 만들 필요가 없습니다. 운영 부담만 늘립니다.
  * **D:** ASG와 함께 쓸 때 대상 유형은 `ip`를 쓸 수 없고 수동 등록은 확장 시 인스턴스를 놓치게 됩니다.
  * **E:** Elastic IP는 로드 밸런서 대상 등록과 무관하고, 인스턴스마다 붙이는 것은 낭비입니다.
</details>

## 정답 빠른 확인표

| 문항 | 정답 | 핵심 키워드 |
|---|---|---|
| Q1 | C | 사용량 약정, 패밀리·리전 변경 가능 → Compute Savings Plans |
| Q2 | B | 특정 AZ 용량 보장, 약정 없음 → On-Demand Capacity Reservation |
| Q3 | D | 150,000 IOPS, 99.999% → io2 Block Express |
| Q4 | B | 자주 접근하는 대용량 순차 처리, 최저 비용 → st1 |
| Q5 | A | 무중단 gp2→gp3 → Elastic Volumes |
| Q6 | C | EBS는 AZ 종속 → 스냅샷으로 이동 |
| Q7 | D | 같은 볼륨 동시 사용 → io2 Multi-Attach |
| Q8 | C | 임시 고속 스크래치 → Instance Store |
| Q9 | A | 고정 IP + TCP/UDP + 초저지연 → NLB |
| Q10 | B | 서드파티 방화벽 어플라이언스 → GWLB |
| Q11 | A | AZ별 대상 수 불균형 → 교차 영역 분산 켜기 |
| Q12 | C | 앱 장애 감지 → ASG의 ELB 헬스 체크 |
| Q13 | A | 반복 패턴, 미리 확장 → Predictive Scaling |
| Q14 | D | Spot 절감 + 중단 대비 → 혼합 인스턴스 정책 |

## 시험 직전 핵심 암기표

### EC2 구매 옵션

| 상황 | 정답 후보 |
|---|---|
| 장기 사용, 구성 변경 가능 | Compute Savings Plans |
| 장기 사용, 구성 고정 | Reserved Instances 또는 EC2 Instance Savings Plans |
| 중단 가능한 배치 작업 | Spot |
| 중단 불가, 단기 | On-Demand |
| 특정 AZ 용량 보장 | On-Demand Capacity Reservation |
| 서버 단위 소프트웨어 라이선스 재사용, 규정 준수 | Dedicated Hosts |

### EBS 볼륨 유형

| 요구사항 | 정답 후보 | 한 줄 사양(AWS 페이지 기준) |
|---|---|---|
| 대부분의 일반 워크로드, 부트 볼륨 | gp3 | 기본 3,000 IOPS, 125 MiB/s, 최대 80,000 IOPS, 2,000 MiB/s |
| 최고 성능, 지연 시간 민감 DB | io2 Block Express | 최대 256,000 IOPS, 4,000 MB/s, 내구성 99.999% |
| 자주 접근하는 순차 처리량 | st1 | 최대 500 MB/s, 부트 볼륨 불가 |
| 드물게 접근하는 콜드 데이터 | sc1 | 최대 250 MB/s, 부트 볼륨 불가 |
| 임시 고속 저장소 | Instance Store | 중지·종료 시 데이터 손실 |
| 같은 볼륨을 여러 인스턴스에 | io2 Multi-Attach | 같은 AZ, Nitro 기반, 최대 16대 |

### 로드 밸런서 선택

| 요구사항 | 정답 후보 |
|---|---|
| HTTP/HTTPS, 경로·호스트 기반 라우팅, WAF | ALB |
| TCP/UDP, 초저지연, 고정 IP | NLB |
| 서드파티 가상 어플라이언스 | GWLB |
| 이전 세대 | CLB(ALB 또는 NLB로 마이그레이션 권장) |

### Auto Scaling

| 요구사항 | 정답 후보 |
|---|---|
| 지표에 따라 자동 조정 | Target Tracking(처음 쓴다면 권장) |
| 시간이 정해진 증감 | Scheduled Scaling |
| 반복 패턴을 학습해 미리 확장 | Predictive Scaling |
| 앱 수준 장애까지 감지해 교체 | ELB 헬스 체크 켜기 |
| Spot 중단 대비 | 혼합 인스턴스 정책 + Capacity Rebalancing |
