### Question 1 (Multi-Select: Select TWO) — Cross-Account KMS & S3 Access with IAM Roles
A financial analytics company stores sensitive parquet files in an Amazon S3 bucket (`analytics-prod-data`) in **Account A**. The bucket is encrypted using a customer managed AWS KMS key (`KMS-Prod-Key`) also located in **Account A**. A data science team operates an Amazon EC2 instance with an attached IAM role (`DataScienceRole`) in **Account B**. The team needs to read objects from the S3 bucket in Account A.

Which combination of steps will allow `DataScienceRole` to read and decrypt the objects? **(Select TWO.)**

- **A.** Attach an identity-based policy to `DataScienceRole` in Account B granting `s3:GetObject` on `arn:aws:s3:::analytics-prod-data/*` and `kms:Decrypt` on `KMS-Prod-Key`.
- **B.** Update the S3 bucket policy in Account A to allow `arn:aws:iam::Account-B-ID:role/DataScienceRole` to perform `s3:GetObject`, and update the KMS key policy in Account A to allow `DataScienceRole` to perform `kms:Decrypt`.
- **C.** Configure the trust policy of `DataScienceRole` in Account B to list Account A as a trusted principal.
- **D.** Enable S3 Bucket Keys on `analytics-prod-data` so that `DataScienceRole` does not require explicit KMS key policy permissions across accounts.
- **E.** Attach an AWS managed `AdministratorAccess` policy to `DataScienceRole` in Account B, which automatically bypasses resource-based policies in Account A.

<details>
<summary><b>정답 및 상세 해설 보기 (Click to expand)</b></summary>

* **정답:** **A, B**
* **핵심 출제 포인트:** **교차 계정(Cross-Account) S3 + SSE-KMS 접근 시 양방향 권한 부여 규칙**
* **상세 분석:**
  * 동일한 계정 내에서는 리소스 기반 정책(S3 Bucket Policy 등)만 있거나 자격 증명 기반 정책(IAM Role Policy)만 있어도 접근이 허용됩니다(단, KMS 키는 기본 키 정책이 IAM 활성화를 허용할 때).
  * 그러나 **서로 다른 계정(Account A와 Account B)** 간에 리소스에 접근할 때는 **양쪽 모두의 명시적 허용(Explicit Allow)**이 필요합니다.
  * **A (정답):** 요청 주체인 Account B의 `DataScienceRole`에 S3 읽기(`s3:GetObject`) 및 KMS 복호화(`kms:Decrypt`) 권한을 부여해야 합니다.
  * **B (정답):** 리소스 소유자인 Account A의 S3 버킷 정책과 KMS 키 정책 모두에서 Account B의 `DataScienceRole` ARN을 신뢰할 수 있는 보안 주체(Principal)로 지정하고 해당 액션을 허용해야 합니다.
* **오답 소거:**
  * **C:** `DataScienceRole`은 Account B의 EC2가 사용하는 역할이므로, Trust Policy에는 EC2 서비스(`ec2.amazonaws.com`)가 들어가야 합니다. Account A를 Trust Policy에 넣는 것은 Account A가 Account B의 역할을 수임(Assume)할 때 사용하는 방식입니다.
  * **D:** S3 Bucket Key는 KMS API 호출 비용과 지연 시간을 줄여주는 기능일 뿐, 교차 계정 KMS 권한 검증을 우회하지 않습니다.
  * **E:** 교차 계정 접근에서는 한쪽 계정의 관리자 권한(`AdministratorAccess`)이 다른 계정의 리소스 정책을 절대 우회할 수 없습니다.
</details>

### Question 2 (Single-Select) — IAM Policy Evaluation Logic & Permissions Boundaries
An organization uses AWS Organizations. An engineer in a member account has an IAM user with a **Permissions Boundary** attached that allows `s3:*`, `ec2:*`, and `dynamodb:*`. The engineer assumes an IAM role (`AppDeployRole`) that has the `AmazonS3FullAccess` managed policy attached, and passes an inline **Session Policy** during the `sts:AssumeRole` API call that allows only `s3:GetObject` and `s3:PutObject`. Additionally, an **SCP (Service Control Policy)** attached to the member account's Organizational Unit (OU) explicitly denies `s3:PutObject` unless the request uses TLS (`aws:SecureTransport = true`).

If the engineer attempts to upload an object to S3 over an unencrypted HTTP connection using the assumed role credentials, what will happen and why?

- **A.** The upload will succeed because the `AmazonS3FullAccess` policy on `AppDeployRole` overrides the Session Policy restrictions.
- **B.** The upload will be denied because the Permissions Boundary attached to the engineer's IAM user restricts the assumed role's session.
- **C.** The upload will be denied because an explicit Deny in the SCP overrides all Allow statements across all policy types.
- **D.** The upload will succeed if the S3 bucket policy explicitly allows `s3:PutObject` for `AppDeployRole`, because resource-based policies bypass SCPs.

<details>
<summary><b>정답 및 상세 해설 보기 (Click to expand)</b></summary>

* **정답:** **C**
* **핵심 출제 포인트:** **IAM 정책 평가 로직(Policy Evaluation Logic) 및 다중 정책 교집합/Explicit Deny 우선순위**
* **상세 분석:**
  * AWS IAM에서 요청이 최종 허용(Allow)되려면 **Explicit Deny가 전혀 없어야 하며**, 동시에 적용되는 모든 정책 계층(SCP, Resource-based Policy, Permissions Boundary, Session Policy, Identity-based Policy)에서 권한 교집합을 통과해야 합니다.
  * **C (정답):** 가장 최상위 가드레일인 SCP에서 `aws:SecureTransport = false`(암호화되지 않은 HTTP)인 `s3:PutObject` 요청에 대해 **명시적 거부(Explicit Deny)**를 설정했습니다. AWS에서 Explicit Deny는 다른 어떤 정책의 Allow보다 항상 최우선으로 적용되어 즉시 요청을 차단합니다.
* **오답 소거:**
  * **A:** `AssumeRole` 시 전달된 Session Policy는 역할의 권한을 확장하지 못하며, 역할의 Identity-based Policy와 **교집합(Intersection)**으로 작동하여 권한을 축소합니다.
  * **B:** 사용자의 IAM User에 연결된 Permissions Boundary는 해당 사용자가 직접 수행하는 작업에만 적용되며, 사용자가 **수임(Assume)한 IAM Role의 세션에는 전이되지 않습니다.** (역할 자체에 Permissions Boundary가 걸려 있어야 적용됩니다.)
  * **D:** Resource-based Policy(S3 버킷 정책)가 동일 계정 내 IAM 정책을 보완할 수는 있으나, **SCP의 Explicit Deny를 우회할 수는 없습니다.**
</details>

### Question 3 (Single-Select) — Role Chaining & Maximum Session Duration Limitation
A DevOps automation pipeline runs on a dedicated CI/CD server in a Shared Services account. The server uses an instance profile (`CICDRole`) to assume an intermediate role (`SecurityAuditRole`) in a Security account. From that session, the script immediately attempts to assume a target role (`ProdDeployRole`) in a Production account to run a 3-hour database migration. However, the script consistently fails at the 1-hour mark with an `ExpiredToken` error, even though the `MaxSessionDuration` property on `ProdDeployRole` has been configured to 12 hours (`43200` seconds).

What is the root cause of this failure, and how should the solutions architect resolve it?

- **A.** `STS` tokens generated via Role Chaining are strictly limited to a maximum of 1 hour; configure `CICDRole` to directly assume `ProdDeployRole` instead of chaining through `SecurityAuditRole`.
- **B.** The `MaxSessionDuration` on `CICDRole` is still set to 1 hour; increase `MaxSessionDuration` on `CICDRole` to 12 hours.
- **C.** EC2 Instance Metadata Service (IMDSv2) refreshes role credentials every 60 minutes; modify the SDK retry logic to call `sts:GetCallerIdentity` every 30 minutes.
- **D.** Cross-account `sts:AssumeRole` calls are hard-capped at 1 hour regardless of `MaxSessionDuration`; switch to `sts:GetFederationToken` which supports up to 36 hours.

<details>
<summary><b>정답 및 상세 해설 보기 (Click to expand)</b></summary>

* **정답:** **A**
* **핵심 출제 포인트:** **역할 체이닝(Role Chaining)의 1시간 세션 제한 규정**
* **상세 분석:**
  * **역할 체이닝(Role Chaining)**이란, 이미 IAM Role을 수임(Assume)하여 얻은 임시 자격 증명을 사용해 **또 다른 두 번째 IAM Role을 연속으로 수임**하는 것을 말합니다(`CICDRole` → `SecurityAuditRole` → `ProdDeployRole`).
  * **A (정답):** AWS STS 보안 정책상 **역할 체이닝을 통해 발급된 임시 자격 증명의 최대 세션 시간은 1시간(3,600초)으로 엄격히 제한**됩니다. 대상 역할(`ProdDeployRole`)의 `MaxSessionDuration`을 12시간으로 늘려놓았더라도, 체이닝으로 호출하면 1시간을 초과하여 `DurationSeconds`를 지정할 수 없으며 1시간 뒤 만료됩니다. 이를 해결하려면 중간 역할을 거치지 않고 `CICDRole`이 `ProdDeployRole`을 **직접 수임(Direct AssumeRole)**하도록 아키텍처를 변경해야 합니다.
* **오답 소거:**
  * **B:** `CICDRole`의 최대 세션 시간을 늘려도 역할 체이닝 자체의 1시간 한도는 풀리지 않습니다.
  * **C:** IMDSv2는 만료 전 자동으로 백그라운드에서 자격 증명을 갱신하며, `GetCallerIdentity`는 세션 시간을 연장해 주는 API가 아닙니다.
  * **D:** 단일 단계의 교차 계정 `AssumeRole`은 대상 역할의 설정에 따라 최대 12시간까지 지원됩니다.
</details>

### Question 4 (Multi-Select: Select THREE) — Troubleshooting Access Denied in IAM Roles
A solutions architect is troubleshooting an `AccessDenied` error when an AWS Lambda function (`OrderProcessorFunction`) attempts to write items to an Amazon DynamoDB table (`OrdersTable`) encrypted with a customer managed KMS key. Both resources are in the same AWS account and region. The architect inspects the Lambda execution role (`LambdaExecRole`) and confirms it has `dynamodb:PutItem` permission on `OrdersTable`.

Which THREE potential issues could be causing this `AccessDenied` error? **(Select THREE.)**

- **A.** `LambdaExecRole` lacks `kms:GenerateDataKey` and `kms:Decrypt` permissions on the customer managed KMS key used by `OrdersTable`.
- **B.** A VPC Endpoint Policy attached to the Gateway VPC Endpoint for DynamoDB does not allow `dynamodb:PutItem` for `LambdaExecRole`.
- **C.** The trust policy of `LambdaExecRole` does not include `dynamodb.amazonaws.com` as a trusted service principal.
- **D.** A Permissions Boundary attached to `LambdaExecRole` omits `dynamodb:PutItem` or the required KMS actions.
- **E.** The Lambda function's execution role has not had `sts:AssumeRole` explicitly granted inside its own identity-based permissions policy.
- **F.** DynamoDB streams are enabled on `OrdersTable`, and `LambdaExecRole` lacks `dynamodb:GetRecords` permission.

<details>
<summary><b>정답 및 상세 해설 보기 (Click to expand)</b></summary>

* **정답:** **A, B, D**
* **핵심 출제 포인트:** **실무형 트러블슈팅 — 동일 계정 내 IAM Role 권한 거부 원인 분석**
* **상세 분석:**
  * **A (정답):** DynamoDB 테이블이 고객 관리형 KMS 키(CMK)로 암호화되어 있다면, 테이블에 데이터를 쓸 때(`PutItem`) DynamoDB 서비스가 호출자(`LambdaExecRole`)의 권한을 대리하여 데이터 키를 생성해야 하므로 **`kms:GenerateDataKey` 및 `kms:Decrypt` 권한**이 반드시 필요합니다.
  * **B (정답):** Lambda 함수가 VPC 내부에 연결되어 있고 Gateway VPC Endpoint를 통해 DynamoDB와 통신하는 경우, **VPC 엔드포인트 정책(Endpoint Policy)**이 추가적인 리소스 경계 역할을 합니다. 엔드포인트 정책에서 해당 주체나 액션을 허용하지 않으면 `AccessDenied`가 발생합니다.
  * **D (정답):** 역할에 `dynamodb:PutItem` 권한 정책이 붙어 있더라도, 해당 역할에 **Permissions Boundary**가 설정되어 있고 그 경계 안에 DynamoDB 및 KMS 권한이 포함되어 있지 않으면 교집합 원칙에 따라 차단됩니다.
* **오답 소거:**
  * **C:** `LambdaExecRole`은 Lambda 함수가 사용하는 역할이므로 Trust Policy에는 `lambda.amazonaws.com`만 있으면 됩니다. `dynamodb.amazonaws.com`은 필요하지 않습니다.
  * **E:** AWS Lambda 서비스가 실행 역할을 수임하는 것은 Trust Policy에 의해 제어되며, 역할 자신의 권한 정책(Identity-based policy)에 `sts:AssumeRole`을 넣을 필요가 없습니다.
  * **F:** 테이블에 항목을 쓰는(`PutItem`) 작업은 스트림을 읽는(`GetRecords`) 권한과 무관합니다.
</details>

### Question 5 (Single-Select) — Amazon EKS IAM Roles for Service Accounts (IRSA)
A company runs containerized microservices on an Amazon EKS cluster. One pod runs a legacy batch job that requires read/write access to an Amazon S3 bucket, while other pods on the exact same EC2 worker node should have zero access to S3. The security team prohibits storing static AWS access keys in Kubernetes Secrets or container images, and rejects granting S3 permissions to the EKS worker node's EC2 instance profile.

How should a solutions architect configure access to meet these requirements with minimal operational overhead?

- **A.** Enable IMDSv2 on the EKS worker nodes and configure the pod to assume an IAM role using the node's instance profile with a session policy.
- **B.** Associate an IAM OIDC provider with the EKS cluster, create an IAM role with a web identity trust policy scoped to the pod's Kubernetes Service Account, and annotate the Service Account with the role ARN.
- **C.** Create an IAM user for the legacy batch job, rotate its access keys every 24 hours using AWS Secrets Manager, and mount the secret as a volume into the pod.
- **D.** Deploy a sidecar container running `kube2iam` to intercept metadata requests and configure SAML 2.0 federation between the EKS control plane and AWS IAM.

<details>
<summary><b>정답 및 상세 해설 보기 (Click to expand)</b></summary>

* **정답:** **B**
* **핵심 출제 포인트:** **Amazon EKS의 IRSA (IAM Roles for Service Accounts) 아키텍처**
* **상세 분석:**
  * 단일 EC2 워커 노드 위에는 여러 개의 Pod가 함께 실행됩니다. 만약 EC2 인스턴스 프로파일(Node Role)에 S3 권한을 주면, 같은 노드 위의 모든 Pod가 IMDS를 통해 S3에 접근할 수 있게 되어 **최소 권한 원칙(Least Privilege)**에 위배됩니다.
  * **B (정답):** **IRSA(IAM Roles for Service Accounts)**는 EKS 클러스터를 **OIDC(OpenID Connect) 자격 증명 공급자**로 IAM에 등록하고, 특정 Kubernetes Service Account(Namespace + ServiceAccount 이름)만 수임할 수 있도록 조건(`StringEquals` on `:sub`)이 걸린 **Web Identity Trust Policy**를 가진 IAM Role을 연결하는 AWS 네이티브 모범 사례입니다. 이를 통해 Pod 단위로 격리된 임시 자격 증명을 안전하게 주입할 수 있습니다.
* **오답 소거:**
  * **A:** IMDSv2를 활성화하더라도 노드 레벨의 인스턴스 프로파일 권한은 해당 노드 위 모든 Pod에 공유되므로 격리 요구사항을 충족하지 못합니다.
  * **C:** 정적 액세스 키 저장을 금지한다는 보안 팀 요구사항에 정면으로 위배됩니다.
  * **D:** `kube2iam`은 구식 서드파티 워크어라운드이며 운영 오버헤드가 크고 SAML 2.0은 EKS Pod 인증 방식이 아닙니다.
</details>

### Question 6 (Single-Select) — SAML 2.0 Federation & Session Tags for Granular Access Control
An enterprise uses an on-premises SAML 2.0-compliant Identity Provider (IdP) to federate thousands of employees into AWS. Employees are mapped to a single shared IAM role (`EnterpriseDeveloperRole`) upon login. Each employee belongs to a specific `CostCenter` and `Project` in the corporate directory. The company wants to ensure that when developers create or manage Amazon EC2 instances, they can only terminate instances that belong to their own `CostCenter` and `Project`, without creating separate IAM roles for every project team.

Which solution meets these requirements?

- **A.** Configure the IdP to pass `CostCenter` and `Project` as SAML assertions mapped to `https://aws.amazon.com/SAML/Attributes/PrincipalTag:CostCenter` and `Project`, update the role's trust policy to allow `sts:TagSession`, and use `aws:PrincipalTag` conditions in the role's permissions policy.
- **B.** Configure the IdP to pass `CostCenter` and `Project` in the `RoleSessionName` SAML attribute, and use a `StringLike` condition on `aws:userid` in the permissions policy to match the resource tags.
- **C.** Enable AWS IAM Identity Center (AWS SSO) and create a separate permission set for each combination of `CostCenter` and `Project`, attaching inline policies to each set.
- **D.** Attach a resource-based policy directly to every EC2 instance that checks the caller's SAML assertion attributes at the time of the `ec2:TerminateInstances` API call.

<details>
<summary><b>정답 및 상세 해설 보기 (Click to expand)</b></summary>

* **정답:** **A**
* **핵심 출제 포인트:** **SAML 2.0 연동에서의 세션 태그(Session Tags) 및 ABAC(속성 기반 액세스 제어) 구현**
* **상세 분석:**
  * 수천 명의 직원이 **단일 공유 IAM Role(`EnterpriseDeveloperRole`)**을 사용하면서도 개인별 속성(부서, 프로젝트)에 따라 리소스 접근을 동적으로 통제하려면 **SAML 세션 태그(Session Tags)**를 사용해야 합니다.
  * **A (정답):** IdP가 SAML 어설션에 `https://aws.amazon.com/SAML/Attributes/PrincipalTag:<TagKey>` 형식으로 속성을 담아 보내고, IAM Role의 Trust Policy에 `sts:AssumeRoleWithSAML`과 함께 **`sts:TagSession`** 액션을 허용하면, 해당 속성이 세션의 `PrincipalTag`로 주입됩니다. 이후 권한 정책에서 `aws:PrincipalTag/CostCenter == aws:ResourceTag/CostCenter` 조건을 걸면 역할 개수를 늘리지 않고도 세밀한 동적 제어가 가능합니다.
* **오답 소거:**
  * **B:** `RoleSessionName`은 단일 문자열(예: 이메일) 용도이며, 다중 속성을 파싱하여 리소스 태그와 비교하는 것은 유지보수가 불가능하고 표준 패턴이 아닙니다.
  * **C:** 프로젝트와 비용 센터 조합마다 별도의 권한 집합(Permission Set)을 만드는 것은 역할 폭발(Role Explosion)을 유발하며 문제의 전제("별도 역할을 만들지 않음")에 어긋납니다.
  * **D:** Amazon EC2 인스턴스에는 S3 버킷이나 KMS 키 같은 **리소스 기반 정책(Resource-based Policy) 자체가 존재하지 않습니다.**
</details>

### Question 7 (Single-Select) — EC2 Instance Metadata Service (IMDSv2) & SSRF Mitigation
A company hosts a public-facing web application on Amazon EC2 instances behind an Application Load Balancer. The EC2 instances use an IAM instance profile with permissions to read configuration secrets from AWS Secrets Manager and write logs to Amazon S3. A recent security audit revealed a Server-Side Request Forgery (SSRF) vulnerability in a third-party web library that could allow an attacker to query local HTTP endpoints on the EC2 instance.

Which immediate infrastructure-level configuration change will best protect the EC2 instance's IAM role credentials from being exfiltrated via the SSRF vulnerability without modifying application code?

- **A.** Rotate the IAM role's temporary credentials manually every 15 minutes using an AWS Lambda scheduled function.
- **B.** Enforce IMDSv2 on the EC2 instances by setting `HttpTokens` to `required` and setting `HttpPutResponseHopLimit` to `1`.
- **C.** Block all outbound traffic to `169.254.169.254` in the EC2 instance's Security Group egress rules.
- **D.** Replace the EC2 instance profile with an IAM user's access keys stored as environment variables inside `/etc/environment`.

<details>
<summary><b>정답 및 상세 해설 보기 (Click to expand)</b></summary>

* **정답:** **B**
* **핵심 출제 포인트:** **IMDSv2(Instance Metadata Service Version 2)의 SSRF 방어 메커니즘**
* **상세 분석:**
  * 기존의 IMDSv1은 단순 `HTTP GET` 요청만으로 `http://169.254.169.254/latest/meta-data/iam/security-credentials/` 경로에서 IAM Role의 임시 자격 증명을 탈취할 수 있어 SSRF 공격에 취약했습니다.
  * **B (정답):** **IMDSv2(`HttpTokens=required`)**를 강제하면, 메타데이터를 조회하기 전에 먼저 **`HTTP PUT` 요청과 특수 헤더(`X-aws-ec2-metadata-token-ttl-seconds`)**를 보내 세션 토큰을 발급받아야 합니다. 대부분의 웹 SSRF 취약점은 단순 `GET` 요청만 유도할 수 있으므로 `PUT` 및 커스텀 헤더 요구사항을 통과하지 못해 자격 증명 탈취가 원천 차단됩니다. 또한 `HttpPutResponseHopLimit=1` 설정은 컨테이너나 리버스 프록시를 통한 패킷 포워딩도 막아줍니다.
* **오답 소거:**
  * **A:** IAM Role 자격 증명은 AWS가 자동 관리하므로 수동 교체가 불가능하며, 15분마다 교체해도 SSRF 취약점이 열려 있으면 즉시 다시 탈취됩니다.
  * **C:** `169.254.169.254`는 인스턴스 내부의 링크 로컬(Link-local) 가상 인터페이스이므로 **Security Group(보안 그룹) 규칙이 적용되지 않으며**, 차단할 경우 정상적인 애플리케이션도 IAM Role 자격 증명을 받지 못하게 됩니다.
  * **D:** 정적 액세스 키를 파일이나 환경 변수에 저장하는 것은 보안 모범 사례에 역행하는 최악의 선택입니다.

### Question 8 (Multi-Select: Select TWO) — Cross-Account EventBridge & AWS Lambda Execution
A centralized monitoring account (**Account M**) collects security findings and sends events to an Amazon EventBridge custom event bus. When a high-severity event arrives, EventBridge in Account M needs to trigger a remediation AWS Lambda function (`AutoRemediateFunc`) residing in a workload account (**Account W**).

Which TWO configurations are required to allow EventBridge in Account M to invoke the Lambda function in Account W? **(Select TWO.)**

- **A.** Add a resource-based policy statement to `AutoRemediateFunc` in Account W that allows `events.amazonaws.com` (or Account M's EventBridge rule ARN) to perform `lambda:InvokeFunction`.
- **B.** Create an IAM role in Account M with `lambda:InvokeFunction` permissions for `AutoRemediateFunc` in Account W, and attach this role to the EventBridge rule target in Account M.
- **C.** Update the execution role of `AutoRemediateFunc` in Account W to trust `events.amazonaws.com` in Account M.
- **D.** Configure an EventBridge event bus in Account W, route the event from Account M to Account W's event bus, and let Account W's EventBridge invoke `AutoRemediateFunc` using its resource-based policy.
- **E.** Attach an IAM role in Account W directly to the EventBridge rule in Account M as the execution target role.

<details>
<summary><b>정답 및 상세 해설 보기 (Click to expand)</b></summary>

* **정답:** **A, D** *(참고: AWS 아키텍처상 교차 계정 Lambda 직접 호출 또는 Event Bus 경유 방식의 핵심 원리)*
* **핵심 출제 포인트:** **서비스 간 교차 계정 호출(Cross-Account Service Invocation) 시 IAM Role vs Resource-Based Policy 구분**
* **상세 분석:**
  * AWS EventBridge 규칙이 타겟을 호출할 때, 타겟 유형에 따라 IAM Role을 사용하는 경우와 Resource-based Policy를 사용하는 경우가 엄격히 나뉩니다.
  * **AWS Lambda 함수를 EventBridge 타겟으로 호출할 때는 IAM Role을 사용하지 않고, 오직 Lambda 함수의 리소스 기반 정책(Resource-based Policy)만을 사용**합니다.
  * **A (정답):** Account M의 EventBridge 규칙이 Account W의 Lambda 함수를 직접 타겟으로 호출하려면, Account W의 `AutoRemediateFunc` 리소스 기반 정책에 Account M의 EventBridge 규칙 ARN을 Principal로 지정해 `lambda:InvokeFunction`을 허용해야 합니다.
  * **D (정답):** AWS가 권장하는 또 다른 표준 교차 계정 패턴은 Account M의 EventBridge 규칙이 Account W의 **Event Bus**로 이벤트를 전달(이때 Account M의 IAM Role을 사용해 `events:PutEvents` 호출)하고, Account W의 EventBridge 규칙이 로컬 Lambda 함수의 리소스 기반 정책을 통해 `AutoRemediateFunc`를 호출하는 구조입니다.
* **오답 소거:**
  * **B, E:** EventBridge는 EC2나 Kinesis 같은 타겟에는 IAM Role을 사용하지만, **Lambda 타겟에는 Execution Role(타겟 역할)을 지정할 수 없습니다.**
  * **C:** Lambda 함수의 Execution Role(실행 역할)은 **Lambda 함수 내부 코드가 다른 AWS 서비스에 접근할 때** 사용하는 신분증이지, 외부 서비스가 Lambda 함수를 호출(Invoke)할 때 검증하는 정책이 아닙니다.

The company's internal security policy strictly forbids creating long-lived IAM users or storing static AWS access keys on any on-premises server. The company already operates an internal Public Key Infrastructure (PKI) that issues X.509 certificates to all on-premises servers.

Which solution meets these security requirements with the least administrative overhead?

- **D.** Create an IAM role with an EC2 trust policy, generate an instance profile ARN, and pass the ARN as a parameter in the AWS CLI configuration file on the on-premises servers.

### Question 10 (Single-Select) — Service Control Policies (SCP) vs. IAM Role Permissions & Root User
A security architect at a large enterprise wants to ensure that **no one** in any member account within the `Production` Organizational Unit (OU)—including local account `AdministratorAccess` IAM roles and even the member account's **Root user**—can disable AWS CloudTrail logging or delete the central CloudTrail S3 log bucket. However, the centralized security team's break-glass IAM role (`CentralSecOpsRole`) in those member accounts must still be able to modify CloudTrail configurations during emergency incident response.

How should the security architect design the policy to achieve this?

- **A.** Attach an SCP to the `Production` OU with an explicit `Deny` on `cloudtrail:StopLogging` and `s3:DeleteBucket`, using a `Condition` block with `StringNotLike` on `aws:PrincipalArn` specifying `arn:aws:iam::*:role/CentralSecOpsRole`.
- **B.** Attach a Permissions Boundary to the Root user and all IAM roles in the member accounts that denies `cloudtrail:StopLogging`, excluding `CentralSecOpsRole`.
- **C.** Remove `cloudtrail:*` permissions from the `AdministratorAccess` managed policy across all member accounts and grant it exclusively to `CentralSecOpsRole`.
- **D.** Configure an SCP that denies `cloudtrail:StopLogging` for `aws:PrincipalType = Root`, and rely on IAM identity-based policies to restrict all other IAM roles.

<details>
<summary><b>정답 및 상세 해설 보기 (Click to expand)</b></summary>

* **정답:** **A**
* **핵심 출제 포인트:** **SCP(Service Control Policy)의 적용 범위(멤버 계정 Root 사용자 포함) 및 예외 처리 조건문(`aws:PrincipalArn`)**
* **상세 분석:**
  * 멤버 계정의 **Root 사용자**까지 제어할 수 있는 유일한 정책 도구는 **AWS Organizations의 SCP(Service Control Policy)**입니다. (IAM 정책이나 Permissions Boundary는 멤버 계정의 Root 사용자에게 적용되지 않습니다.)
  * **A (정답):** `Production` OU에 SCP를 연결하여 `cloudtrail:StopLogging`과 `s3:DeleteBucket`을 명시적으로 차단(`Deny`)하되, `Condition` 블록에 **`"StringNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/CentralSecOpsRole" }`** 조건을 추가합니다. 이렇게 하면 멤버 계정의 Root 사용자 및 일반 관리자는 차단되면서도, 오직 `CentralSecOpsRole` 역할을 수임한 보안 팀만 예외적으로 긴급 작업을 수행할 수 있습니다.
* **오답 소거:**
  * **B:** **Permissions Boundary는 IAM User와 IAM Role에만 연결할 수 있으며, AWS 계정의 Root 사용자에게는 연결할 수 없습니다.**
  * **C:** `AdministratorAccess`는 AWS 관리형 정책(AWS Managed Policy)이므로 사용자가 내용을 수정할 수 없으며, 수정하더라도 멤버 계정의 Root 사용자는 여전히 모든 권한을 가집니다.
  * **D:** SCP에서 Root만 막고 나머지를 일반 IAM 정책에 의존하면, 멤버 계정의 `AdministratorAccess` 역할을 가진 관리자가 자신의 IAM 정책을 수정하여 제한을 쉽게 풀 수 있습니다.
</details>
