## 0. 먼저 정리: 정책(Policy)과 문장(Statement)의 구성 요소

```json
{
  "Version": "2012-10-17",                  // ← 정책(Policy) 레벨
  "Id": "ExamplePolicy",                    // ← 정책(Policy) 레벨 (선택)
  "Statement": [                            // ← 정책(Policy) 레벨 (필수)
    {
      "Sid": "AllowS3Read",                 // ← 문장(Statement) 요소 (선택)
      "Effect": "Allow",                    // ← 문장 요소 (필수)
      "Principal": { "AWS": "arn:aws:iam::111122223333:root" },  // ← 리소스 기반 정책/신뢰 정책에서만
      "Action": "s3:GetObject",             // ← 문장 요소 (필수)
      "Resource": "arn:aws:s3:::my-bucket/*", // ← 문장 요소 (ID 기반 정책에서 필수)
      "Condition": { "Bool": { "aws:SecureTransport": "true" } }  // ← 문장 요소 (선택)
    }
  ]
}
```

| 구분 | 요소 | 한글 표기(강의 자막) | 필수 여부 / 비고 |
|---|---|---|---|
| **정책 레벨** | `Version` | 버전 | 정책 언어 버전. 항상 `2012-10-17` 사용 (**문장의 요소가 아님!**) |
| | `Id` | - | 선택 (정책 식별자) |
| | `Statement` | 문장 | 필수 (1개 이상) |
| **문장 레벨** | `Sid` | 시드 | 선택 (문장 식별자) |
| | `Effect` | 효과 | 필수 (`Allow` / `Deny`) |
| | `Principal` | **원칙**(= 주체) | **리소스 기반 정책, 신뢰 정책에서만** 사용. ID 기반 정책에서는 사용 불가 |
| | `Action` | **조치**(= 작업) | 필수 (`NotAction`도 가능) |
| | `Resource` | 리소스 | ID 기반 정책에서 필수 (`NotResource`도 가능) |
| | `Condition` | 조건 | 선택 |

> **암기 포인트:** 강의 한글 자막에서 `Principal`은 "원칙"(principle이 아님!), `Action`은 "조치"로 번역되어 헷갈리기 쉽습니다. 이 두 단어가 보이면 **영어로 머릿속 변환**(원칙 → Principal, 조치 → Action)한 뒤 풀이하세요.
> **암기 문구:** 문장(Statement)은 **S-E-P-A-R-C** = Sid, Effect, Principal, Action, Resource, Condition. **Version은 Statement 밖**에 있다!

## Question 0 (Sample): IAM Policy Statement Elements — 오답이었던 원본 문제

**Scenario:**
An IAM policy consists of one or more statements. Which of the following is **NOT** an element of a statement within an IAM policy?

* **A.** Effect
* **B.** Principal
* **C.** Version
* **D.** Action
* **E.** Resource

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **C**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** IAM 정책 JSON의 **정책 레벨 요소(Version, Id, Statement)** 와 **문장 레벨 요소(Sid, Effect, Principal, Action, Resource, Condition)** 를 구분할 수 있는지 묻는 문제입니다. "NOT"이 들어간 문제이므로 **문장 안에 들어가지 않는 것**을 골라야 합니다.
* **정답 분석 (C):** `Version`은 정책 문서 전체의 **정책 언어 버전**(예: `2012-10-17`)을 나타내는 **정책 최상위 요소**입니다. `Statement` 배열 **바깥**에 위치하므로 문장(Statement)의 구성 요소가 아닙니다.
* **오답 분석:**
  * **A. Effect:** 문장이 `Allow`인지 `Deny`인지를 정하는 **필수** 문장 요소입니다.
  * **B. Principal:** 누가(어떤 계정/사용자/역할/서비스가) 접근하는지를 지정하는 문장 요소입니다. **리소스 기반 정책(S3 버킷 정책 등)과 역할의 신뢰 정책**에서 사용하고, ID 기반 정책에서는 쓰지 않습니다. 하지만 "문장 요소가 **아닌** 것"을 묻는 문제이므로, **ID 기반 정책에서 안 쓴다고 해서 문장 요소가 아닌 것은 아닙니다.** (이 부분이 가장 흔한 함정!)
  * **D. Action:** 허용/거부할 API 작업(예: `s3:GetObject`)을 지정하는 **필수** 문장 요소입니다. (한글 자막: "조치")
  * **E. Resource:** 대상 리소스의 ARN을 지정하는 문장 요소입니다.
* **복습 팁:** 한글 자막의 "원칙"은 Principal, "조치"는 Action입니다. 이름이 낯설어서 오답으로 보이는 보기를 고르지 않도록 **영문으로 환원해서** 판단하세요.
</details>

## Question 1: Required vs. Optional Elements

**Scenario:**
A solutions architect is reviewing a custom **identity-based** IAM policy that will be attached to an IAM role. The security team's checklist asks which statement elements are **mandatory** (as opposed to optional or not applicable). Which **TWO** of the following elements are **required** in every statement of an identity-based policy? (Choose TWO.)

* **A.** Sid
* **B.** Effect
* **C.** Condition
* **D.** Principal
* **E.** Action

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **B, E**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 문장 요소 중 **필수(Required)** 와 **선택(Optional)** 을 구분하는 문제입니다. 요소별 필수 여부를 정확히 알아야 "Choose TWO" 유형도 안전하게 풀 수 있습니다.
* **정답 분석 (B, E):**
  * **Effect:** `Allow` 또는 `Deny`. 모든 문장에 반드시 있어야 합니다.
  * **Action:** 대상 API 작업. (`NotAction`으로 대체 가능하지만 둘 중 하나는 반드시 필요)
  * (참고) ID 기반 정책에서는 `Resource`(또는 `NotResource`)도 필수이지만, 이 문제의 보기에는 포함되지 않았습니다.
* **오답 분석:**
  * **A. Sid:** 문장을 식별하기 위한 **선택** 요소입니다. (같은 정책 안에서 유일해야 함)
  * **C. Condition:** 특정 조건(IP, MFA, 태그, 시간 등)에서만 적용하려 할 때 쓰는 **선택** 요소입니다.
  * **D. Principal:** ID 기반 정책에서는 **사용 불가**입니다. 정책이 붙은 사용자/그룹/역할 자신이 곧 주체이기 때문입니다. (리소스 기반 정책에서는 필수)
</details>

## Question 2: Principal Element in Identity-Based Policy

**Scenario:**
A solutions architect creates a new IAM policy using the JSON editor in the AWS Management Console. The policy is intended to be attached to an IAM group and includes the following element in its statement:

`"Principal": { "AWS": "arn:aws:iam::111122223333:user/alice" }`

When the architect tries to save the policy, the console returns the error: **"Policy document should not specify a principal."** What is the cause of the error and how should it be fixed?

* **A.** The `Version` element must be changed to `2008-10-17` so that the `Principal` element is supported.
* **B.** The `Sid` element is missing; add a `Sid` to uniquely identify the principal.
* **C.** The `Effect` must be changed to `Deny` to allow a principal to be specified.
* **D.** Identity-based policies do not support the `Principal` element because the principal is the identity the policy is attached to. Remove the `Principal` element, or use a resource-based policy if the principal must be specified.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **D**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **ID 기반 정책(Identity-based)** 과 **리소스 기반 정책(Resource-based)** 의 차이, 그리고 `Principal` 요소가 쓰이는 위치를 묻는 문제입니다.
* **정답 분석 (D):** ID 기반 정책(사용자/그룹/역할에 붙이는 정책)은 **"붙은 대상 = 주체"** 이므로 `Principal`을 쓸 수 없습니다. 쓰면 콘솔이 위 에러를 반환합니다. 주체를 명시해야 하는 상황이라면 **S3 버킷 정책, SQS 큐 정책, KMS 키 정책, IAM 역할의 신뢰 정책** 같은 **리소스 기반 정책**을 사용해야 합니다.
* **오답 분석:**
  * **A:** `Version`은 `Principal` 지원 여부와 무관하며, 항상 `2012-10-17`을 권장합니다.
  * **B:** `Sid`는 선택 요소이며 주체를 식별하는 기능이 아닙니다.
  * **C:** `Effect`(Allow/Deny)와 `Principal` 사용 가능 여부는 관계가 없습니다.
</details>

## Question 3: Version Element and Policy Variables

**Scenario:**
A company has 200 developers. Each developer must be able to read and write objects only under their own prefix `home/<username>/` in the S3 bucket `corp-dev-data`. The architect wants to attach **one single policy** to the `Developers` IAM group. The policy uses the variable `${aws:username}` in the `Resource` element, but all developers receive `AccessDenied`. The policy document begins with `"Version": "2008-10-17"`. What should the architect do?

* **A.** Change the policy's `Version` element to `"2012-10-17"` so that the `${aws:username}` policy variable is evaluated at request time.
* **B.** Replace `${aws:username}` with `*` so all developers can access all prefixes.
* **C.** Create 200 inline policies, one for each developer, with each username hard-coded.
* **D.** Add a `Sid` to the statement to enable policy variable substitution.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** `Version` 요소의 **실제 역할**을 묻는 문제입니다. `Version`은 정책의 "수정 이력"이 아니라 **정책 언어 문법 버전**이며, **정책 변수(Policy Variables, 예: `${aws:username}`)는 `2012-10-17`에서만 동작**합니다.
* **정답 분석 (A):** `2008-10-17` 버전에서는 `${aws:username}`이 **변수가 아닌 일반 문자열**로 취급되어 실제 리소스 경로와 매칭되지 않으므로 거부됩니다. `2012-10-17`로 바꾸면 요청 시점에 요청자의 사용자 이름으로 치환되어 **그룹 하나, 정책 하나**로 200명을 관리할 수 있습니다. (`Version`을 생략하면 기본값이 `2008-10-17`이 되므로 항상 명시하세요.)
* **오답 분석:**
  * **B:** 최소 권한 원칙 위반 (모든 개발자가 서로의 데이터를 볼 수 있음).
  * **C:** 운영 오버헤드가 크고, 인원이 바뀔 때마다 정책을 수정해야 합니다.
  * **D:** `Sid`는 단순 식별자이며 변수 치환 기능과 무관합니다.
</details>

## Question 4: Policy Evaluation Logic — Explicit Deny

**Scenario:**
IAM user `bob` is a member of the `Developers` group, which has the **AWS managed policy** `AmazonS3FullAccess` attached. A separate **inline policy** on `bob` contains an explicit `Deny` for `s3:DeleteObject` on the bucket `prod-logs`. No permissions boundary or SCP is in use. What happens when `bob` tries to delete an object in `prod-logs`?

* **A.** Allowed, because AWS managed policies always take precedence over inline policies.
* **B.** Allowed, because the `Allow` in the group policy is evaluated first.
* **C.** Denied, because an explicit `Deny` in any applicable policy overrides any `Allow`.
* **D.** Denied only if `bob` also has a permissions boundary attached.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **C**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **IAM 정책 평가 로직**의 3단계 원칙을 묻는 SAA 최빈출 개념입니다.
  1. **기본값은 암묵적 거부(Implicit Deny)**
  2. 적용되는 정책 중 **하나라도 명시적 거부(Explicit Deny)** 가 있으면 → **무조건 거부**
  3. 명시적 거부가 없고 **명시적 허용(Allow)** 이 있으면 → 허용
* **정답 분석 (C):** 정책의 종류(AWS 관리형/고객 관리형/인라인)나 평가 순서와 무관하게 **명시적 Deny는 모든 Allow보다 우선**합니다.
* **오답 분석:**
  * **A:** 정책 유형에 따른 우선순위는 존재하지 않습니다.
  * **B:** "먼저 평가된 Allow"라는 개념은 없습니다. 모든 정책을 종합해 평가합니다.
  * **D:** 권한 경계(Permissions Boundary)는 **최대 권한의 상한선**을 제한할 뿐, 명시적 Deny의 효력 여부와는 무관합니다.
</details>

## Question 5: Cross-Account Access — Both Sides Must Allow

**Scenario:**
A company stores reports in an S3 bucket in **Account A**. The bucket policy grants `s3:GetObject` to `"Principal": { "AWS": "arn:aws:iam::<AccountB-ID>:root" }`. An IAM user in **Account B** attempts to download an object and receives `AccessDenied`. The IAM user currently has no policies attached that mention S3. What is the cause?

* **A.** Bucket policies cannot be used for cross-account access; only S3 ACLs can.
* **B.** The IAM user in Account B also needs an identity-based policy that allows `s3:GetObject` on the bucket, because cross-account access requires an explicit `Allow` on **both** sides.
* **C.** The IAM user must be moved to Account A to access the bucket.
* **D.** The `Principal` in the bucket policy must be changed to `"*"` to cover all accounts.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **B**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **같은 계정 내 접근**과 **교차 계정(Cross-Account) 접근**의 평가 방식 차이입니다.
  * **같은 계정:** ID 기반 정책 **또는** 리소스 기반 정책 중 한쪽에서 허용되면 충분합니다(명시적 Deny 없을 때).
  * **교차 계정:** **리소스 계정(A)의 리소스 기반 정책** + **요청자 계정(B)의 ID 기반 정책** **양쪽 모두** Allow가 필요합니다.
* **정답 분석 (B):** 버킷 정책은 Account B를 신뢰(`root` 지정은 "B 계정에 권한을 위임"한다는 의미)할 뿐, B 계정 안의 **특정 사용자에게 권한을 직접 주는 것이 아닙니다.** B 계정 관리자가 해당 사용자에게 `s3:GetObject`를 허용하는 ID 기반 정책을 부여해야 접근이 성공합니다.
* **오답 분석:**
  * **A:** 버킷 정책으로 교차 계정 접근이 가능합니다.
  * **C:** 사용자를 이동할 필요가 없습니다.
  * **D:** `Principal: "*"`는 모든 주체에게 개방하는 것이므로 보안 위험이며, 문제의 원인도 아닙니다.
</details>

## Question 6: Resource Element — Bucket ARN vs. Object ARN

**Scenario:**
An IAM policy attached to a role contains the following statement:

`"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::reports-bucket"`

Users assuming the role receive `AccessDenied` when they try to download or upload objects in `reports-bucket`. What is the cause and the fix?

* **A.** Add a `Principal` element listing every user who assumes the role.
* **B.** `GetObject` and `PutObject` are object-level actions. Change the `Resource` to `arn:aws:s3:::reports-bucket/*`.
* **C.** Add the `s3:ListAllMyBuckets` action to the statement.
* **D.** Remove the `Version` element so that AWS applies the latest policy language by default.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **B**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** S3 정책에서 **버킷 레벨 ARN**과 **객체 레벨 ARN**을 구분하는 문제입니다. (실무/시험 모두 단골 실수)
* **정답 분석 (B):**
  * `arn:aws:s3:::reports-bucket` → **버킷 자체** (예: `s3:ListBucket`, `s3:GetBucketLocation`)
  * `arn:aws:s3:::reports-bucket/*` → **버킷 안의 객체들** (예: `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`)
  * 객체 작업에는 반드시 `/*`가 붙은 ARN이 필요합니다. 목록 조회까지 필요하면 `Resource`에 **두 ARN을 모두** 나열합니다.
* **오답 분석:**
  * **A:** ID 기반 정책에는 `Principal`을 쓸 수 없습니다.
  * **C:** `ListAllMyBuckets`는 계정의 버킷 목록 조회 권한이며, 객체 접근과 무관합니다.
  * **D:** `Version`을 생략하면 기본값이 **오래된 `2008-10-17`** 이 적용되므로 오히려 권장되지 않습니다.
</details>

## Question 7: Condition Element — Enforcing HTTPS (Encryption in Transit)

**Scenario:**
A compliance requirement states that **all** requests to an S3 bucket must use encryption in transit (TLS). Requests over plain HTTP must be rejected regardless of who sends them. Which bucket policy approach meets this requirement?

* **A.** A statement with `Effect: Allow` for all principals only when `aws:SecureTransport` is `true`.
* **B.** Enable default encryption with SSE-KMS on the bucket.
* **C.** A statement that denies access when `aws:SourceIp` is not within the corporate IP range.
* **D.** A statement with `Effect: Deny`, `Principal: "*"`, `Action: "s3:*"`, `Resource` set to the bucket and bucket objects, and the condition `"Bool": { "aws:SecureTransport": "false" }`.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **D**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **Condition 요소**와 **Deny 문장**을 조합해 보안 요구사항을 "강제"하는 패턴입니다. `aws:SecureTransport`는 요청이 HTTPS(TLS)인지 여부를 나타내는 전역 조건 키입니다.
* **정답 분석 (D):** `Deny` + `aws:SecureTransport = false` 조합은 **다른 정책에서 어떤 Allow가 있어도** HTTP 요청을 차단합니다(명시적 Deny 우선). 버킷 정책이므로 `Principal`이 필요하며, `Resource`에는 **버킷 ARN과 객체 ARN(`/*`) 둘 다** 넣는 것이 모범 사례입니다.
* **오답 분석:**
  * **A:** `Allow` + `true` 조건은 "HTTPS면 허용"일 뿐, **다른 Allow 정책으로 HTTP 접근이 허용되는 것을 막지 못합니다.** 강제하려면 Deny를 사용해야 합니다.
  * **B:** SSE-KMS는 **저장 데이터(at rest)** 암호화이며 전송 구간 암호화와 무관합니다.
  * **C:** IP 제한은 접근 위치 통제일 뿐, TLS 사용 여부와는 무관합니다.
</details>

## Question 8: Deny + NotAction — Requiring MFA

**Scenario:**
A company requires all IAM users to authenticate with MFA before performing **any** AWS action. However, new users must still be able to register their own MFA device and change their own password so they can comply. Which policy statement design meets this requirement?

* **A.** `Effect: Allow`, `NotAction` listing the MFA/password self-management actions, `Resource: "*"`, with condition `aws:MultiFactorAuthPresent` is `true`.
* **B.** `Effect: Deny`, `NotAction` listing the MFA/password self-management actions, `Resource: "*"`, with condition `BoolIfExists: { "aws:MultiFactorAuthPresent": "false" }`.
* **C.** `Effect: Deny`, `Action: "iam:*"`, `Resource: "*"`, with condition `aws:MultiFactorAuthPresent` is `false`.
* **D.** `Effect: Allow`, `Action: "*"`, `Resource: "*"`, with condition `aws:MultiFactorAuthPresent` is `true`.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **B**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** `NotAction`의 의미와 **"Allow + NotAction ≠ 거부"** 함정, 그리고 MFA 강제 패턴(AWS 공식 문서의 대표 예제)을 묻는 문제입니다.
* **정답 분석 (B):** `Deny` + `NotAction`은 "나열된 작업**만 제외하고** 나머지는 모두 거부"를 의미합니다. MFA가 없는 세션에서는 MFA 등록/비밀번호 변경 같은 자기 관리 작업만 가능하고, 그 외 모든 작업은 거부됩니다. `BoolIfExists`를 쓰는 이유는, **장기 액세스 키 등 MFA 키 자체가 요청에 없는 경우**에도 조건이 `false`로 평가되어 거부되도록 하기 위함입니다.
* **오답 분석:**
  * **A:** `Allow` + `NotAction`은 "나열된 것을 제외한 **모든 작업을 허용**"하므로 사실상 광범위한 관리자 권한을 부여하게 됩니다. 의도와 정반대입니다.
  * **C:** `iam:*`만 거부하면 다른 서비스(S3, EC2 등) 작업은 MFA 없이도 가능하고, MFA 등록에 필요한 IAM 작업까지 막아 버립니다.
  * **D:** Allow만으로는 **다른 정책으로 부여된 권한**이 MFA 없이 사용되는 것을 막지 못합니다. 강제는 Deny로 해야 합니다.
</details>

## Question 9: Customer Managed Policy Versions (≠ `Version` Element)

**Scenario:**
A security team maintains one custom permissions policy that is attached to 40 IAM roles. After the latest policy update, several applications stop working. The team needs to **revert to the previous permissions immediately** without detaching and reattaching the policy on each role. Which approach should they have used?

* **A.** Use an inline policy in each of the 40 roles and edit each one individually.
* **B.** Use an AWS managed policy and ask AWS Support to roll back the change.
* **C.** Use a customer managed policy, which keeps up to five versions, and set the previous version as the default version.
* **D.** Change the `Version` element in the policy JSON to the previous date (for example, `2008-10-17`) to revert the policy.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **C**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **JSON의 `Version` 요소**(정책 언어 버전)와 **관리형 정책의 버전 관리 기능**(정책 수정 이력)을 구별하는 문제입니다. 샘플 문제(Question 0)에서 헷갈렸던 "버전"과 연결되는 개념입니다.
* **정답 분석 (C):** **고객 관리형 정책(Customer Managed Policy)** 은 수정할 때마다 새 버전이 저장되며 **최대 5개 버전**까지 보관됩니다. 이전 버전을 **기본 버전(Default version)** 으로 지정하면 연결된 **모든 역할/사용자/그룹에 즉시 반영**됩니다. 또한 하나의 정책을 여러 대상에 재사용하므로 관리 효율도 높습니다.
* **오답 분석:**
  * **A:** 인라인 정책은 개별 엔터티에 종속되어 재사용이 불가능하고 롤백 기능도 없습니다.
  * **B:** AWS 관리형 정책은 AWS가 관리하며 사용자가 수정/롤백할 수 없습니다.
  * **D:** JSON의 `Version`은 **정책 문법 버전**일 뿐 "수정 이력"이 아닙니다. 날짜를 바꾼다고 이전 권한으로 복구되지 않으며, 오히려 정책 변수 등 일부 기능이 동작하지 않게 됩니다.
</details>

## Question 10: Principal Element with `aws:PrincipalOrgID`

**Scenario:**
A company uses AWS Organizations with 80 member accounts. A shared-services account hosts an S3 bucket containing common datasets that **all accounts in the organization**, including accounts created in the future, must be able to read. The solution must minimize operational overhead and must not expose the data outside the organization. Which solution meets these requirements?

* **A.** Add a bucket policy statement that allows `s3:GetObject` with `Principal: "*"` and the condition `"StringEquals": { "aws:PrincipalOrgID": "<org-id>" }`.
* **B.** Add every member account ID to the `Principal` element of the bucket policy and update the policy each time a new account is created.
* **C.** Make the bucket public and rely on application-level authentication.
* **D.** Create an IAM user in the shared-services account for each member account and distribute their access keys.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 리소스 기반 정책에서 **`Principal` + `Condition`을 조합**해 조직(Organization) 전체에 접근을 허용하는 최신 모범 사례입니다.
* **정답 분석 (A):** `aws:PrincipalOrgID` 조건 키를 사용하면 **같은 AWS Organization에 속한 모든 계정의 주체**만 접근하도록 제한할 수 있습니다. `Principal: "*"`이지만 조건 때문에 조직 외부는 접근할 수 없고, **새로 생성되는 계정도 자동으로 포함**되어 정책 수정이 필요 없습니다. (교차 계정이므로 각 계정에서는 ID 기반 정책으로 `s3:GetObject`를 허용해야 실제 사용이 가능합니다 — Question 5 참고.)
* **오답 분석:**
  * **B:** 계정이 추가될 때마다 정책을 수정해야 하고, 정책 크기 제한에도 걸릴 수 있어 운영 부담이 큽니다.
  * **C:** 퍼블릭 개방은 조직 외부 노출 금지 요구사항 위반입니다.
  * **D:** 장기 자격 증명(액세스 키) 배포는 보안 모범 사례에 어긋나고 관리 부담이 큽니다.
</details>
