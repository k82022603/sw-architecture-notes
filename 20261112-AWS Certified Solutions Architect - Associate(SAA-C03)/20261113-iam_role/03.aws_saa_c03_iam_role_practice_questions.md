## Question 1: EC2 Access to S3 (AWS Service Trusted Entity)

**Scenario:**
A company runs a mission-critical application on Amazon EC2 instances that needs to read and write sensitive files to an Amazon S3 bucket. The security team strictly prohibits storing long-term AWS access keys on the EC2 instances or in the application source code. Which solution meets these requirements with the LEAST operational overhead?

* **A.** Create an IAM user with S3 permissions, generate access keys, and store them in AWS Systems Manager Parameter Store as SecureString parameters.
* **B.** Create an IAM role with `ec2.amazonaws.com` as the trusted entity, attach an S3 access policy, and assign the role to the EC2 instances using an instance profile.
* **C.** Create a bucket policy on the S3 bucket that allows access from the public IP addresses of the EC2 instances.
* **D.** Configure AWS STS to generate temporary credentials using an IAM user's credentials via a cron job running every hour on the EC2 instances.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **B**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** AWS 리소스(EC2)가 다른 AWS 서비스(S3)에 접근할 때, 장기 자격 증명(Access Key)을 하드코딩하지 않고 안전하게 권한을 부여하는 표준 아키텍처를 묻는 문제입니다.
* **정답 분석 (B):** EC2 인스턴스에 **IAM Role**을 연결(Instance Profile 활용)하면, 인스턴스 메타데이터 서비스(IMDSv2)를 통해 AWS STS로부터 임시 보안 자격 증명을 자동으로 발급받고 주기적으로 갱신합니다. 운영 부담(Operational Overhead)이 가장 적고 보안성이 뛰어납니다.
* **오답 분석:**
  * **A:** 여전히 장기 자격 증명(IAM User의 Access Key)을 생성하여 관리해야 하므로 보안 모범 사례에 어긋납니다.
  * **C:** EC2의 퍼블릭 IP는 재시작 시 변경될 수 있으며, IP 기반 제어는 IAM Role 기반 인증보다 관리가 어렵고 안전하지 않습니다.
  * **D:** 임시 자격 증명을 갱신하기 위해 별도의 크론잡(Cron job)과 IAM User 키를 관리하는 것은 불필요한 운영 오버헤드를 발생시킵니다.
</details>

## Question 2: Third-Party SaaS Vendor Access (Confused Deputy Prevention)

**Scenario:**
A financial company wants to grant a third-party SaaS monitoring vendor read-only access to its AWS account to audit resource configurations. The security architect is concerned about the "Confused Deputy" problem, where another customer of the same SaaS vendor might trick the vendor into accessing the financial company's AWS resources. How should the solutions architect configure the IAM role?

* **A.** Configure an IAM role with the vendor's AWS account ID as the trusted entity and require an `sts:ExternalId` condition in the trust policy.
* **B.** Create an IAM user for the vendor and enforce Multi-Factor Authentication (MFA) on the account.
* **C.** Configure an IAM role with Web Identity Federation and require an OIDC token from the vendor.
* **D.** Create an IAM role with a custom trust policy that restricts access based on the vendor's corporate CIDR IP range.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 제3자(3rd-party) AWS 계정에 Cross-Account Role을 부여할 때 발생할 수 있는 **혼동된 대리자 문제(Confused Deputy Problem)**의 해결책을 묻는 SAA-C03 단골 문제입니다.
* **정답 분석 (A):** 외부 벤더의 AWS 계정을 신뢰할 수 있는 엔티티(`AWS account`)로 설정할 때, 벤더가 제공한 고유 식별자인 **External ID**를 신뢰 정책의 조건(`"StringEquals": {"sts:ExternalId": "..."}`)으로 추가해야 합니다. 이를 통해 다른 고객이 벤더를 속여 내 계정에 접근하는 것을 원천 차단합니다.
* **오답 분석:**
  * **B:** 제3자 벤더에게 영구적인 IAM User를 생성해 주는 것은 AWS 보안 모범 사례에 위배됩니다.
  * **C:** AWS 계정 간 연동에는 OIDC(Web Identity)가 아닌 `AWS account` 유형의 신뢰 엔티티를 사용합니다.
  * **D:** IP 주소 제한만으로는 동일한 SaaS 벤더 인프라(동일 IP 대역)에서 발생하는 혼동된 대리자 공격을 방어할 수 없습니다.
</details>

## Question 3: Mobile Application User Authentication (Web Identity Federation)

**Scenario:**
A startup is developing a mobile gaming application that will scale to millions of users. Users need to upload their profile pictures directly to an Amazon S3 bucket without routing traffic through the application's backend servers. Users should be able to sign in using their existing Google or Apple accounts. Which solution is MOST scalable and secure?

* **A.** Programmatically create a dedicated IAM user for each mobile user upon registration and embed the access keys in the mobile app.
* **B.** Use Amazon Cognito Identity Pools to exchange Google/Apple OIDC tokens for temporary AWS credentials via an IAM role configured with Web Identity.
* **C.** Set up SAML 2.0 federation between Google/Apple and AWS IAM to allow mobile users to assume an IAM role.
* **D.** Configure the S3 bucket to allow public write access and validate user tokens using an S3 Bucket Policy.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **B**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 수백만 명의 일반 소비자(모바일/웹 앱 사용자)에게 소셜 로그인을 통해 AWS 리소스(S3, DynamoDB 등) 직접 접근 권한을 부여하는 아키텍처입니다.
* **정답 분석 (B):** 외부 소셜 로그인(Google, Apple 등 OIDC 공급자)을 사용하는 경우 **Amazon Cognito 자격 증명 풀(Identity Pools)**과 **Web Identity 유형의 IAM Role**을 결합합니다. 사용자가 소셜 로그인으로 받은 토큰을 STS(`AssumeRoleWithWebIdentity`)에 전달하면 임시 AWS 자격 증명이 발급되어 안전하게 S3에 직접 업로드할 수 있습니다.
* **오답 분석:**
  * **A:** IAM User는 AWS 계정당 기본 한도(5,000명)가 존재하므로 수백만 명 규모로 확장할 수 없으며, 모바일 앱에 키를 내장하는 것은 심각한 보안 취약점입니다.
  * **C:** SAML 2.0은 주로 기업 내부 임직원(Active Directory 등)의 사내 통합 인증(SSO)에 사용되며, 일반 소비자용 소셜 로그인에는 적합하지 않습니다.
  * **D:** S3 버킷을 퍼블릭 쓰기(Public Write)로 여는 것은 데이터 유출 및 악성 파일 업로드 위험이 있어 절대 금지됩니다.
</details>

## Question 4: Enterprise On-Premises Active Directory Integration (SAML 2.0)

**Scenario:**
An enterprise organization has 5,000 employees managed in an on-premises Microsoft Active Directory (AD). The company wants employees to access the AWS Management Console using their existing corporate credentials without creating separate IAM users in AWS. Different AD groups (e.g., Developers, Auditors, Admins) must map to different permission sets in AWS. Which solution meets these requirements?

* **A.** Configure SAML 2.0 federation using Active Directory Federation Services (ADFS) and create IAM roles with SAML 2.0 as the trusted entity mapped to AD groups.
* **B.** Use Amazon Cognito User Pools to sync on-premises AD passwords and generate AWS access keys for each employee.
* **C.** Create a single shared IAM user for each department and distribute the credentials via an internal portal.
* **D.** Set up AWS STS `AssumeRoleWithWebIdentity` to authenticate employees directly against the on-premises LDAP server.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 온프레미스 기업 디렉토리(Active Directory)의 임직원 계정을 이용해 AWS 콘솔에 싱글 사인온(SSO)으로 접근하고 부서별 권한을 매핑하는 방법입니다.
* **정답 분석 (A):** 기업용 IdP(ADFS, Okta 등)와 AWS를 연동할 때는 **SAML 2.0 Federation**을 사용합니다. IAM에서 IdP를 등록하고, `SAML 2.0 federation`을 신뢰 엔티티로 갖는 IAM Role(예: DeveloperRole, AdminRole)을 생성한 뒤 AD 그룹과 매핑하면 직원이 사내 계정으로 AWS 콘솔에 바로 로그인할 수 있습니다. (참고: 최신 환경에서는 AWS IAM Identity Center를 사용할 수도 있습니다.)
* **오답 분석:**
  * **B:** Cognito User Pools는 주로 외부 웹/모바일 앱 고객 인증용이며, 온프레미스 AD 비밀번호를 동기화하여 액세스 키를 발급하는 방식은 적절하지 않습니다.
  * **C:** 여러 직원이 하나의 IAM User 자격 증명을 공유하는 것은 감사 추적(CloudTrail)이 불가능해지며 보안 모범 사례에 위배됩니다.
  * **D:** `AssumeRoleWithWebIdentity`는 OIDC/소셜 로그인용 API이며, 온프레미스 AD/SAML 연동에는 `AssumeRoleWithSAML` API가 사용됩니다.
</details>

## Question 5: GitHub Actions CI/CD Pipeline Deployment (OIDC Custom Trust Policy)

**Scenario:**
A DevOps team uses GitHub Actions to deploy infrastructure changes to their AWS account. Previously, they stored long-lived IAM user access keys as GitHub Secrets, which violated the company's new security policy requiring short-lived credentials only. How can the team securely authenticate GitHub Actions workflows to AWS without storing static credentials?

* **A.** Configure GitHub as an IAM OIDC Identity Provider in AWS and create an IAM role with a trust policy restricting `sts:AssumeRoleWithWebIdentity` to the specific GitHub repository.
* **B.** Launch a self-hosted GitHub runner on an Amazon EC2 instance and assign an IAM user to the instance.
* **C.** Create an IAM role with `AWS account` as the trusted entity and add GitHub's corporate AWS account ID.
* **D.** Store the IAM user access keys in AWS Secrets Manager and have GitHub Actions retrieve them using an unauthenticated API call.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 외부 CI/CD 도구(GitHub Actions, GitLab CI 등)에서 장기 액세스 키 없이 AWS에 안전하게 배포하기 위한 **OIDC(OpenID Connect) 기반 자격 증명 연동**을 묻는 최신 출제 경향 문제입니다.
* **정답 분석 (A):** AWS IAM에 GitHub을 **OIDC 자격 증명 공급자(Identity Provider)**로 등록하고, 해당 GitHub 저장소(`repo:org/repo:*`) 조건이 포함된 신뢰 정책(Web Identity / Custom Trust Policy)을 가진 IAM Role을 생성합니다. 워크플로우 실행 시 GitHub이 발급한 JWT 토큰을 AWS STS에 제출해 단기 임시 자격 증명을 받아 배포를 수행합니다.
* **오답 분석:**
  * **B:** EC2 인스턴스에는 IAM User가 아닌 IAM Role을 할당해야 하며, 기존 SaaS형 GitHub Actions 환경을 불필요하게 셀프 호스팅으로 전환할 필요가 없습니다.
  * **C:** GitHub Actions 워크플로우는 AWS 계정이 아닌 OIDC 토큰 기반으로 인증합니다.
  * **D:** 인증되지 않은(Unauthenticated) API 호출로 AWS Secrets Manager에서 비밀 값을 가져오는 것은 불가능합니다.
</details>

## Question 6: Cross-Account Access & Session Chaining / Permissions

**Scenario:**
A company has a centralized `Security` AWS account where all security engineers have IAM users, and 50 `Production` AWS accounts. Security engineers need to assume an `AuditRole` in each Production account to investigate incidents. Additionally, security engineers must be authenticated with Multi-Factor Authentication (MFA) before assuming the role. Which combination of configurations is required?

* **A.** In the `Security` account, attach a policy allowing `sts:AssumeRole` on the `AuditRole` ARNs. In each `Production` account, create `AuditRole` trusting the `Security` account with a condition checking `aws:MultiFactorAuthPresent` is true.
* **B.** In each `Production` account, create `AuditRole` trusting `ec2.amazonaws.com` and share the role ARN with the security engineers.
* **C.** Enable AWS IAM Access Analyzer in the `Security` account to automatically grant cross-account permissions to all `Production` accounts.
* **D.** Create a single IAM role in the `Security` account and attach it directly to the resources in the 50 `Production` accounts.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** **교차 계정 접근(Cross-Account Access)의 양방향 신뢰 설정**과 **MFA 강제 조건(Condition)**을 정확히 이해하고 있는지 평가합니다.
* **정답 분석 (A):** Cross-Account Role 전환이 성공하려면 **양쪽 모두**의 허가가 필요합니다.
  1. **신뢰하는 쪽(Production 계정):** `AuditRole`의 신뢰 정책(Trust Policy)에서 `Security` 계정을 신뢰하고, `aws:MultiFactorAuthPresent: "true"` 조건을 명시합니다.
  2. **요청하는 쪽(Security 계정):** 보안 엔지니어의 IAM User/Group 권한 정책에서 대상 `AuditRole`의 ARN에 대해 `sts:AssumeRole` 작업을 허용해야 합니다.
* **오답 분석:**
  * **B:** 대상 주체가 EC2 서비스가 아니라 다른 AWS 계정의 사용자이므로 `AWS account`를 신뢰 엔티티로 지정해야 합니다.
  * **C:** IAM Access Analyzer는 외부로 공유된 리소스를 탐지하고 분석하는 도구이지, 권한을 부여하는 도구가 아닙니다.
  * **D:** IAM Role은 계정(Account) 단위의 리소스이므로 한 계정의 IAM Role을 다른 계정의 리소스에 직접 연결할 수 없습니다.
</details>

## Question 7: Lambda Execution Role & Least Privilege (Permissions Boundary)

**Scenario:**
A company allows application developers to create their own AWS Lambda functions and associated IAM execution roles in a shared development account. However, the security team must ensure that developers cannot create a Lambda execution role with administrative privileges (e.g., `AdministratorAccess`) to escalate their own privileges. What is the MOST effective way to enforce this guardrail?

* **A.** Attach an IAM Permissions Boundary to all developer IAM users/roles and require that any IAM role created by developers must also have that same Permissions Boundary attached.
* **B.** Configure an AWS Config rule to delete any Lambda function that uses an administrative role every 24 hours.
* **C.** Change the trusted entity of all Lambda execution roles to `s3.amazonaws.com`.
* **D.** Remove `iam:CreateRole` permissions from developers and require them to use the AWS root user for Lambda deployments.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 개발자에게 IAM Role 생성 권한(`iam:CreateRole`)을 위임하면서도 **권한 상승(Privilege Escalation)을 방지**하기 위한 **권한 경계(Permissions Boundary)** 개념을 묻는 문제입니다.
* **정답 분석 (A):** **IAM Permissions Boundary**는 엔티티(User 또는 Role)가 가질 수 있는 **최대 권한의 상한선**을 정의합니다. 개발자가 새로운 Lambda 실행 역할을 만들 때 특정 권한 경계를 필수로 부착하도록 조건(`iam:PermissionsBoundary`)을 걸면, 개발자가 역할에 `AdministratorAccess` 정책을 연결하더라도 권한 경계를 벗어나는 작업은 모두 차단됩니다.
* **오답 분석:**
  * **B:** 24시간마다 사후 삭제하는 방식은 그 사이에 발생하는 보안 침해 및 권한 상승을 예방할 수 없습니다(사전 예방 통제 실패).
  * **C:** Lambda 함수가 실행 시 맡는 역할의 신뢰 엔티티는 반드시 `lambda.amazonaws.com`이어야 합니다.
  * **D:** 일상적인 개발 및 배포 작업에 AWS 루트 사용자(Root User)를 사용하는 것은 최악의 보안 안티패턴입니다.
</details>

## Question 8: Dynamic ABAC (Attribute-Based Access Control) with IAM Roles

**Scenario:**
An organization has hundreds of microservices running on Amazon ECS tasks, and each microservice belongs to a specific project (e.g., `Project=Alpha`, `Project=Beta`). Currently, the DevOps team creates a separate IAM role and policy for every single microservice, causing severe administrative overhead. They want to use a single IAM role template where an ECS task can only access AWS Secrets Manager secrets that share the exact same `Project` tag as the task's IAM role. Which feature should they implement?

* **A.** Attribute-Based Access Control (ABAC) using tag-based condition keys (`aws:PrincipalTag/Project` and `aws:ResourceTag/Project`) in the IAM permissions policy.
* **B.** Service Control Policies (SCPs) in AWS Organizations to block cross-project access.
* **C.** Custom trust policies that list every individual Secrets Manager ARN for each ECS task.
* **D.** Resource-based policies on every secret that explicitly deny all IAM roles except one hardcoded ARN.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 수많은 마이크로서비스 환경에서 역할(Role)과 정책이 폭발적으로 늘어나는 문제를 해결하기 위한 **ABAC(속성 기반 액세스 제어)** 전략을 묻는 문제입니다.
* **정답 분석 (A):** **ABAC**를 사용하면 IAM Role(Principal)에 붙은 태그(`aws:PrincipalTag/Project`)와 접근하려는 리소스(Secrets Manager)에 붙은 태그(`aws:ResourceTag/Project`)가 일치할 때만 접근을 허용하는 단일 정책을 작성할 수 있습니다. 새로운 프로젝트가 추가되어도 IAM 정책을 수정할 필요 없이 태그만 부여하면 되므로 관리 부담이 획기적으로 줄어듭니다.
* **오답 분석:**
  * **B:** SCP는 AWS 계정 단위의 최대 권한을 제한하는 도구이므로, 단일 계정 내 마이크로서비스 간의 세밀한 프로젝트 태그 매칭에는 적합하지 않습니다.
  * **C, D:** 개별 ARN을 일일이 하드코딩하는 방식은 기존 방식과 마찬가지로 마이크로서비스가 늘어날 때마다 정책을 계속 수정해야 하는 운영 오버헤드가 발생합니다.
</details>

* **D.** Attach an inline policy to the EC2 instance profile granting `sts:RefreshToken` permissions.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** AWS STS `AssumeRole`로 발급받는 임시 자격 증명의 **기본 세션 만료 시간(1시간)**과 **최대 세션 기간(최대 12시간) 설정**에 관한 실무 트러블슈팅 문제입니다.
* **정답 분석 (A):** `aws sts assume-role` CLI 명령어로 역할을 수임할 때 기본 세션 유효 시간은 **1시간(3,600초)**입니다. 대상 IAM Role의 **Maximum session duration(최대 세션 기간)** 설정을 최대 **12시간(43,200초)**까지 늘린 후, API 호출 시 `--duration-seconds 36000`(10시간) 파라미터를 지정하면 작업이 완료될 때까지 토큰이 만료되지 않습니다. (참고: 역할을 연쇄적으로 수임하는 Role Chaining의 경우에는 최대 1시간으로 제한됩니다.)
* **오답 분석:**
  * **B:** IAM Role은 최대 12시간까지 세션 기간을 설정할 수 있습니다.
  * **C:** IAM Access Analyzer에는 토큰을 자동 갱신하는 기능이 없습니다.
  * **D:** `sts:RefreshToken`이라는 IAM API 권한은 존재하지 않습니다.
</details>

## Question 10: Service-Linked Roles vs. Standard Service Roles

**Scenario:**
A solutions architect is setting up an Amazon EKS cluster and an Elastic Load Balancing (ELB) Auto Scaling group. During setup, AWS automatically creates an IAM role named `AWSServiceRoleForAutoScaling` in the account. Later, a junior administrator tries to delete this role because they do not recognize it, but AWS prevents the deletion. Why did AWS automatically create this role and block its deletion?

* **A.** It is a Service-Linked Role predefined by the AWS service, and it cannot be deleted until all dependent resources (such as Auto Scaling groups) using it are deleted.
* **B.** It is a Cross-Account Role owned by AWS Support, and only AWS Support engineers can modify or delete it.
* **C.** It is an IAM Role protected by an AWS Organizations Service Control Policy (SCP) that blocks `iam:DeleteRole` across all accounts.
* **D.** It is a Web Identity Role created by Amazon Cognito that requires root user credentials for deletion.

<details>
<summary><strong>Click to view Answer & Detailed Explanation</strong></summary>

* **Correct Answer:** **A**

### 상세 해설 (Korean)
* **핵심 출제 포인트:** 일반 **AWS Service Role**과 AWS 서비스가 직접 생성하고 관리하는 **서비스 연결 역할(Service-Linked Role)**의 차이점을 이해하고 있는지 확인하는 문제입니다.
* **정답 분석 (A):** **Service-Linked Role(서비스 연결 역할)**은 Auto Scaling, EKS, RDS, ELB 같은 특정 AWS 서비스와 직접 연결되어 서비스가 사용자를 대신해 하위 리소스를 생성·관리할 수 있도록 AWS가 사전에 정의해 자동 생성하는 특수한 IAM Role입니다. 신뢰 정책과 권한 정책을 사용자가 임의로 수정할 수 없으며, 해당 역할을 참조하는 **모든 연관 리소스(예: Auto Scaling 그룹)를 먼저 삭제하기 전까지는 역할을 삭제할 수 없습니다.**
* **오답 분석:**
  * **B:** AWS Support가 소유한 교차 계정 역할이 아니라 해당 AWS 서비스가 작동하기 위해 계정 내에 생성한 서비스 연결 역할입니다.
  * **C:** 별도의 SCP 설정이 없더라도 서비스 연결 역할 자체의 보호 메커니즘에 의해 사용 중인 리소스가 있으면 삭제가 차단됩니다.
  * **D:** Amazon Cognito 및 Web Identity와는 무관합니다.
</details>
