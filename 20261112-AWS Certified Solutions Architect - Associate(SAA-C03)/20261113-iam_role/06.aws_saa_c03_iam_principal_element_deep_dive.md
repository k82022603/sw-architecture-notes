# IAM Policy의 `Principal` 요소 완전 정복 (AWS SAA-C03)

작성일: 2026-11-17

> **오늘의 질문**
> Which IAM policy element specifies the AWS account, user, role, or service that is being allowed or denied access — and is required in resource-based policies but must NOT be included in identity-based policies?
> **정답: A. Principal**

---

## 1. 한 줄 요약

> **`Principal` = "누가(Who)"** 접근하는가.
> **리소스 기반 정책**에는 **필수**, **ID 기반 정책**에는 **절대 쓰지 않는다.**

이 문서는 "왜 그런지"를 이해해서 외우지 않아도 풀 수 있도록 정리한 것입니다.

---

## 2. 문장(Statement)을 육하원칙으로 읽기

IAM 정책의 문장 요소는 육하원칙처럼 읽으면 쉽습니다.

| 요소 | 질문 | 예시 | 한 줄 설명 |
|---|---|---|---|
| **Effect** | 허용? 거부? | `Allow` / `Deny` | 결과 |
| **Principal** | **누가?** | 계정, 사용자, 역할, 서비스 | **주체** |
| **Action** | 무엇을 하는가? | `s3:GetObject` | API 작업 |
| **Resource** | 무엇에 대해? | `arn:aws:s3:::bucket/*` | 대상 리소스 |
| **Condition** | 어떤 조건에서? | IP, MFA, 태그, 시간 | 선택적 제한 |
| **Sid** | (이름표) | `"AllowRead"` | 문장 식별자, 선택 |

### 문제의 보기 분석

| 보기 | 요소 | 의미 | 왜 정답이 아닌가 |
|---|---|---|---|
| A | **Principal** | **누가** 접근하는가 | **정답** |
| B | Resource | **무엇을** 대상으로 하는가 | 계정/사용자/역할을 지정하는 요소가 아님 |
| C | Sid | 문장의 식별자(이름표) | 접근 주체와 무관 |
| D | Condition | 어떤 **조건**에서 적용되는가 | 주체를 직접 지정하지 않음 (조건 키로 주체를 필터링할 수는 있음 → 7장) |

---

## 3. 왜 Principal은 ID 기반 정책에 쓸 수 없고, 리소스 기반 정책에는 필수일까?

핵심은 **"정책이 어디에 붙어 있는가"** 입니다.

### 3-1. ID 기반 정책 (Identity-based Policy)

* **붙는 곳:** IAM 사용자, 그룹, 역할
* **의미:** "**나(이 정책이 붙은 대상)** 는 **무엇을** 할 수 있다"
* 정책이 붙은 대상이 곧 주체이므로 **Principal이 이미 암묵적으로 정해져 있습니다.**
* 따라서 `Principal`을 쓰면 오류가 납니다.
  > `Policy document should not specify a principal.`

### 3-2. 리소스 기반 정책 (Resource-based Policy)

* **붙는 곳:** S3 버킷, SQS 큐, SNS 토픽, KMS 키, Lambda 함수, Secrets Manager 비밀 등 **리소스**
* **의미:** "**누가** 나(이 리소스)에게 **무엇을** 할 수 있다"
* 리소스는 스스로 "누구" 인지 알 수 없으므로 **주체를 반드시 명시**해야 합니다.
* `Principal`이 없으면 오류가 납니다.
  > `Missing required field Principal`

### 3-3. 비교표

| 구분 | ID 기반 정책 | 리소스 기반 정책 |
|---|---|---|
| 붙는 곳 | 사용자 / 그룹 / 역할 | S3, SQS, SNS, KMS, Lambda 등 리소스 |
| `Principal` | **사용 불가** (정책이 붙은 대상이 주체) | **필수** |
| `Resource` | 필수 | 선택 (정책이 붙은 리소스 자체가 기본 대상) |
| 대표 예 | `AmazonS3FullAccess`, 인라인 정책 | S3 버킷 정책, KMS 키 정책, 역할의 **신뢰 정책** |
| 교차 계정 | 요청자 계정에서 허용 필요 | 리소스 계정에서 주체 지정 |

> **참고:** `Resource` 요소도 같은 논리로 이해됩니다. ID 기반 정책은 "어떤 리소스에?"를 알려줘야 하지만, 리소스 기반 정책은 이미 리소스에 붙어 있으므로 생략할 수 있습니다.

### 3-4. Principal을 쓰지 않는 다른 정책들

다음 정책 유형도 **Principal을 지원하지 않습니다.**

* 권한 경계 (Permissions Boundary)
* 서비스 제어 정책 (SCP, AWS Organizations)
* 세션 정책 (Session Policy)

이 정책들은 "누가"가 아니라 "최대 어디까지"를 정하는 가드레일이기 때문입니다.

## 4. Principal로 지정할 수 있는 대상과 문법

```json
"Principal": { "<타입>": "<값>" }
```

| 유형 | JSON 예시 | 설명 |
|---|---|---|
| **AWS 계정** | `"AWS": "arn:aws:iam::111122223333:root"` 또는 `"AWS": "111122223333"` | 두 표기는 동일. **계정 전체**를 신뢰 (아래 주의 참고) |
| **IAM 사용자** | `"AWS": "arn:aws:iam::111122223333:user/alice"` | 특정 사용자 |
| **IAM 역할** | `"AWS": "arn:aws:iam::111122223333:role/AppRole"` | 특정 역할 (그 역할을 맡은 세션 포함) |
| **역할 세션** | `"AWS": "arn:aws:sts::111122223333:assumed-role/AppRole/session1"` | 특정 세션 |
| **AWS 서비스** | `"Service": "lambda.amazonaws.com"` | AWS 서비스 자체 |
| **연동(Federated) 주체** | `"Federated": "arn:aws:iam::111122223333:saml-provider/ADFS"` | SAML / OIDC (웹 자격 증명) 공급자 |
| **모든 주체(익명 포함)** | `"Principal": "*"` | 모든 사용자. **반드시 Condition으로 제한** |

### ⚠️ 주의: `root`의 의미

`arn:aws:iam::111122223333:root`는 "루트 사용자"가 아니라 **"해당 계정 전체"** 를 뜻합니다.
이렇게 지정하면 **그 계정의 IAM 관리자가 자기 계정의 사용자/역할에게 접근 권한을 위임**할 수 있게 됩니다. 즉 상대 계정의 **모든 사용자에게 자동으로 접근이 허용되는 것이 아닙니다.** (교차 계정에서는 상대 계정의 ID 기반 정책 허용도 필요 → 6장)

### ⚠️ 주의: 삭제된 사용자/역할

정책에 지정된 사용자나 역할을 삭제하면 정책에 ARN 대신 **고유 ID(`AIDA...` / `AROA...`)** 가 표시됩니다.
같은 이름으로 다시 만들어도 **고유 ID가 달라서 기존 정책과 매칭되지 않습니다.** 신뢰 정책이 갑자기 동작하지 않는 흔한 원인입니다.

## 5. Principal이 쓰이는 대표 위치

| 위치 | Principal의 의미 | 예 |
|---|---|---|
| **S3 버킷 정책** | 이 버킷에 접근할 수 있는 주체 | 다른 계정, 조직 전체, CloudFront OAC(서비스) |
| **IAM 역할 신뢰 정책 (Trust Policy)** | 이 역할을 **맡을(AssumeRole) 수 있는** 주체 | EC2 서비스, 다른 계정, SAML IdP, OIDC(GitHub 등) |
| **KMS 키 정책** | 이 키를 사용/관리할 수 있는 주체 | 계정 root, 특정 역할 |
| **SQS / SNS 정책** | 메시지 발행/구독 주체 | SNS 서비스 → SQS |
| **Lambda 리소스 정책** | 이 함수를 호출할 수 있는 주체 | API Gateway, S3, 다른 계정 |
| **Secrets Manager, ECR, API Gateway 등** | 해당 리소스 접근 주체 | 다른 계정의 역할 |
| **VPC 엔드포인트 정책** | 엔드포인트를 통해 접근 가능한 주체 | 보통 `"Principal": "*"` + Condition |

> **신뢰 정책이 "리소스 기반 정책"이라는 점이 중요합니다.** 역할(Role)은 ID이면서 동시에 리소스이기도 합니다. 역할에는 **① 권한 정책(ID 기반, Principal 없음)** 과 **② 신뢰 정책(리소스 기반, Principal 필수)** 이 함께 붙습니다.

## 6. 예제로 이해하기

### 예제 A. S3 버킷 정책 (리소스 기반 → Principal 필수)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowPartnerAccountRead",
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::444455556666:root" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-bucket/*"
  }]
}
```
* **읽는 법:** 계정 `444455556666`이 `my-bucket`의 객체를 읽는 것을 **허용**.
* 교차 계정이므로 `444455556666` 계정에서도 해당 사용자에게 `s3:GetObject`를 허용하는 **ID 기반 정책**이 있어야 실제로 접근됩니다.

### 예제 B. 같은 내용을 ID 기반 정책으로 (Principal 없음)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-bucket/*"
  }]
}
```
* 이 정책은 **붙은 사용자/역할이 곧 주체**이므로 `Principal`이 없습니다. 여기에 `Principal`을 넣으면 저장 시 오류가 납니다.

### 예제 C. 역할 신뢰 정책 (서비스를 Principal로)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
```
* **읽는 법:** EC2 서비스가 이 역할을 **맡을 수 있다**. EC2에 IAM 역할을 붙이는 구조의 핵심입니다.
* `Resource`가 없습니다. 신뢰 정책은 역할 자신에게 붙은 정책이라 대상이 정해져 있기 때문입니다.

### 예제 D. 조직 전체에 개방 (Principal `*` + Condition)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::shared-datasets/*",
    "Condition": {
      "StringEquals": { "aws:PrincipalOrgID": "o-exampleorgid" }
    }
  }]
}
```
* `Principal: "*"`는 위험해 보이지만 **Condition으로 조직 소속 주체만** 통과시킵니다. 새 계정이 조직에 추가되어도 정책 수정이 필요 없습니다. (시험 단골)

### 예제 E. SNS → SQS (서비스 Principal + 혼동된 대리자 방지)

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "sns.amazonaws.com" },
    "Action": "sqs:SendMessage",
    "Resource": "arn:aws:sqs:ap-northeast-2:111122223333:my-queue",
    "Condition": {
      "ArnEquals": { "aws:SourceArn": "arn:aws:sns:ap-northeast-2:111122223333:my-topic" }
    }
  }]
}
```
* 서비스를 Principal로 쓸 때는 `aws:SourceArn` / `aws:SourceAccount` 조건으로 **"내 토픽에서 온 요청만"** 허용하는 것이 모범 사례입니다.

## 7. 헷갈리기 쉬운 것들

### 7-1. `Principal` 요소 vs. `Principal` 관련 조건 키

`Principal` 요소는 **리소스 기반 정책에서만** 쓰지만, **조건 키**는 ID 기반 정책에서도 쓸 수 있습니다.

| 조건 키 | 용도 |
|---|---|
| `aws:PrincipalOrgID` | 요청 주체가 속한 조직 ID |
| `aws:PrincipalArn` | 요청 주체의 ARN 패턴 |
| `aws:PrincipalTag/<key>` | 요청 주체(사용자/역할)의 태그 → **ABAC** |
| `aws:PrincipalType` | 주체 유형 (User, AssumedRole 등) |

→ **보기 D(Condition)가 "주체를 필터링"할 수는 있지만, 주체를 "지정하는 요소"는 Principal** 입니다.

### 7-2. `NotPrincipal`

* "이 주체**를 제외한** 모두"라는 의미의 요소입니다.
* 동작이 복잡하고 실수하기 쉬워 AWS가 **사용을 권장하지 않습니다.** 대신 `Principal: "*"` + `Deny` + `Condition`(`aws:PrincipalArn` 등) 패턴을 권장합니다.

### 7-3. `Principal: "*"` 와 `{"AWS": "*"}`

* 대부분의 경우 **익명 포함 모든 주체**를 뜻하며 사실상 같게 동작합니다.
* 공개 접근(Public Access)이 되므로 S3에서는 **퍼블릭 액세스 차단(Block Public Access)** 설정과 함께 반드시 점검합니다. 이 패턴을 쓸 때는 **Condition으로 제한**하는 것이 원칙입니다.

### 7-4. 같은 계정 vs. 교차 계정 평가

| 상황 | 필요한 허용 |
|---|---|
| **같은 계정**, 리소스 정책의 Principal이 **특정 사용자/역할 ARN** | 리소스 정책만으로도 가능 |
| **같은 계정**, Principal이 **계정 root** | ID 기반 정책도 필요 (위임 구조) |
| **교차 계정** | **양쪽 모두** Allow 필요 (리소스 계정의 리소스 정책 + 요청자 계정의 ID 기반 정책) |
| **명시적 Deny** | 어떤 Allow보다 항상 우선 |

### 7-5. KMS 키 정책의 특수성

KMS는 **키 정책이 접근 제어의 기준**입니다. 키 정책에 `arn:aws:iam::<계정>:root`를 허용하는 문장이 있어야 IAM 정책으로도 키 사용 권한을 위임할 수 있습니다. 이 문장이 없으면 IAM 정책을 아무리 붙여도 키를 쓸 수 없습니다.

## 8. 시험에서 이렇게 나온다 (패턴 정리)

| 키워드 / 상황 | 정답 방향 |
|---|---|
| "누가 접근하는지 지정", "계정/사용자/역할/서비스 지정" | **Principal** |
| "ID 기반 정책에서 사용할 수 **없는** 요소" | **Principal** |
| "리소스 기반 정책에서 **필수**인 요소" | **Principal** |
| "EC2/Lambda가 역할을 맡도록 허용" | 신뢰 정책 `Principal: {"Service": "..."}` |
| "다른 계정에 S3/SQS/KMS 접근 허용" | 리소스 정책에 `Principal`로 계정 지정 + 상대 계정에서 ID 정책 허용 |
| "조직 내 모든 계정에 개방" | `Principal: "*"` + `aws:PrincipalOrgID` 조건 |
| "외부 SaaS 벤더에 역할 부여" | 신뢰 정책 Principal = 벤더 계정 + `sts:ExternalId` 조건 |
| "GitHub Actions / 모바일 소셜 로그인" | 신뢰 정책 `Principal: {"Federated": "..."}` (OIDC) |
| "SAML(ADFS) 연동" | 신뢰 정책 `Principal: {"Federated": "...saml-provider/..."}` |
| "정책 저장 시 `should not specify a principal` 오류" | ID 기반 정책에서 Principal 제거 |
| "정책 저장 시 `Missing required field Principal` 오류" | 리소스 기반 정책에 Principal 추가 |

## 9. 셀프 체크 (영문 4문제)

**Q1.** A bucket policy statement has no `Principal` element and the console returns `Missing required field Principal`. Why?
* A. Bucket policies are resource-based, so `Principal` is required.
* B. The `Version` must be 2008-10-17.
* C. The `Sid` is missing.
* D. The `Condition` is missing.

**Q2.** Which statement about the `Principal` element is TRUE?
* A. It can be used in permissions boundaries to limit a user.
* B. It is required in identity-based policies attached to IAM groups.
* C. It is used in a role's trust policy to define who can assume the role.
* D. It specifies the S3 bucket that a policy applies to.

**Q3.** A company wants an S3 bucket readable by every account in its AWS Organization, including future accounts, with minimal maintenance. Which bucket policy design is best?
* A. List each account's root ARN in `Principal`.
* B. `Principal: "*"` with `aws:PrincipalOrgID` condition.
* C. Create an IAM user in the bucket account for each member account.
* D. Make the bucket public.

**Q4.** An architect creates an identity-based policy for a group that includes `"Principal": {"AWS": "arn:aws:iam::111122223333:user/alice"}`. What happens?
* A. The policy is saved and applies only to alice.
* B. The policy is rejected because identity-based policies cannot contain `Principal`.
* C. The policy is saved but ignored.
* D. The policy is saved only if `Effect` is `Deny`.

<details>
<summary><strong>정답 및 해설</strong></summary>

* **Q1 → A.** 버킷 정책은 리소스 기반 정책이므로 `Principal`이 필수입니다. `Sid`/`Condition`은 선택, `Version`은 `2012-10-17`을 권장합니다.
* **Q2 → C.** 신뢰 정책은 "누가 이 역할을 맡을 수 있는가"를 `Principal`로 지정합니다. A는 권한 경계가 Principal을 지원하지 않으므로 오답, B는 ID 기반 정책에 쓸 수 없으므로 오답, D는 대상 리소스를 지정하는 것은 `Resource`이므로 오답입니다.
* **Q3 → B.** `aws:PrincipalOrgID` 조건으로 조직 소속 주체만 허용하면 새 계정도 자동 포함됩니다. A는 계정 추가마다 수정이 필요하고, C는 장기 자격 증명 관리 부담, D는 퍼블릭 노출이라 오답입니다.
* **Q4 → B.** ID 기반 정책은 정책이 붙은 대상이 주체이므로 `Principal`을 포함하면 저장 시 거부됩니다. `Effect`와 무관합니다.
</details>

## 10. 마지막 암기 카드

```
Principal = Who (누가)       → 리소스 기반 정책: 필수 / ID 기반 정책: 금지
Action    = What (무엇을)
Resource  = On what (어디에) → ID 기반: 필수 / 리소스 기반: 선택
Condition = When/If (조건)
Effect    = Allow / Deny
Version   = 정책 밖(최상위)  → 문장 요소가 아님
```

* **붙는 곳을 보면 답이 보인다:** 사용자/그룹/역할에 붙으면 Principal ❌, 리소스(버킷/큐/키/함수/역할 신뢰 정책)에 붙으면 Principal ✅
* 오류 메시지 두 개를 외워 두기:
  * `Policy document should not specify a principal` → ID 기반 정책에서 **빼라**
  * `Missing required field Principal` → 리소스 기반 정책에 **넣어라**

## 💡 `Principal`은 딱 한 가지만 기억하세요: **"누구(Who)?"**

IAM 정책에서 `Principal`은 "이 리소스에 누가 접근할 수 있는지"를 적어주는 칸입니다. (예: 특정 사용자, 다른 AWS 계정, EC2 서비스 등)

이게 **어디에 쓰이고 어디에 안 쓰이는지**는 이것만 알면 끝납니다.

---

### 🚪 비유로 이해하기

* **1. ID 기반 정책 (내 사원증)**
* **상황:** 내 목에 걸린 사원증입니다. 사원증에는 이미 "내 이름"이 적혀 있습니다.
* **특징:** 내가 누군지 이미 알기 때문에 **"누가(Principal)"를 적을 필요가 없습니다.** (적으면 에러 납니다!)


* **2. 리소스 기반 정책 (건물 현관의 방문자 명부 / 출입문)**
* **상황:** 회사 건물 입구에 붙어 있는 허가증입니다. 문 입장에서는 "앞에 서 있는 사람이 누군지" 모릅니다.
* **특징:** 문 앞에 **"누가 들어올 수 있는지(Principal)"를 반드시 적어주어야** 합니다.

### 📝 딱 3가지만 외우세요 (시험 단골 포인트)

1. **`Principal` = "누가(Who) 접근하는가?"**
2. **리소스 기반 정책(S3 버킷 등)** 👉 **필수!** (문 앞에 명단을 적어야 하므로)
3. **ID 기반 정책(사용자/그룹/역할에 붙는 정책)** 👉 **금지!** (내 사원증에 내 이름을 또 적을 필요가 없으므로)
